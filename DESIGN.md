## DD-001 · Stack: Flutter + Drift with thin native edges ✅

**Context.** Both Android and Windows 11 must be served (REQ-009). The product owner has experience with Flutter + Drift (Spirit Safe). The inbox must update live on new input.

**Choice.**
- **Flutter** for UI and domain logic; **Drift** (SQLite) for storage, with reactive queries (streams) for live lists.
- **SQLite FTS5** for full-text search (REQ-011).
- Platform-specific features (widget, share menu, keyboard shortcut, notifications, whisper.cpp) as thin modules behind interfaces in Dart: Kotlin (Android), C++/Win32 (Windows), C through `dart:ffi` (whisper.cpp).
- **No `local_auth`**: dropped by DD-007.
- **Platform levels:** Android `minSdk = 33`, `targetSdk = 36`; Windows 11 (x86-64). Both of the user's devices run Android 16, so a low floor gains nothing and costs compatibility code. With 33 the branches for the notification permission and per-app language disappear, while an older spare device stays within reach. Flutter itself sits around API 21–24. *(uncertain about the exact current minimum; not binding for this choice)*

**Layer model.**

```
presentation   Flutter widgets, state (e.g. Riverpod)
domain         entities, use cases, InlineTokenRegistry — pure Dart, no platform imports
data           Drift repositories, AttachmentStore, CryptoService
platform       CaptureChannel, ReminderScheduler, SpeechTranscriber, KeyStore, ShareChannel — implemented per platform
```

**Alternatives.** Kotlin + Jetpack Compose (native, but Windows would need a second codebase). Compose Multiplatform (Windows desktop possible, but less mature for this use and no reuse of Spirit Safe knowledge).

**Consequences.** One codebase; the platform boundary is explicit and testable (fakes in unit tests). Extra maintenance for native modules is limited to the `platform` layer.

**Realises:** REQ-009, REQ-011, REQ-016.

## DD-002 · Speech: whisper.cpp in the app, model imported by hand ✅

**Context.** Voice input is wanted, provided it is offline and preserves privacy (REQ-006). Android's system recognition (`createOnDeviceSpeechRecognizer`) is a black box from Google/the manufacturer, with availability of Dutch varying per device. *(verified; API level uncertain: sources mention 31 or 33)*

**Choice.**
- **whisper.cpp** embedded through an **own thin `dart:ffi` binding**, shared by Android and Windows. Existing Flutter plugins only cover Android/iOS. *(uncertain whether a plugin with Windows support exists by now)*
- **The model is not downloaded by the app** (that needs the network, contrary to REQ-003): the user imports the model file once through the file picker. The app checks the SHA-256 against a known list.
- **Recommended model: `ggml-small-q5_1`** (181 MB) — decided after spike S4 (24-09-2026, SPEC Q4): as accurate as `small` (465 MB) at half the memory, clearly better than `base`. Hashes: see `docs/spikes/S4-whisper.md`.
- **Binding through an own C shim** (a few functions with simple parameters) instead of rebuilding whisper's structs directly in Dart; stays stable with new whisper.cpp versions (S4).
- **Audio first:** the recording is first stored encrypted as an attachment, then transcribed asynchronously. A voice note is never lost through a transcription error.
- **The same rule for image input (REQ-064, PO 09-10-2026; spike S6 🔍).** Handwriting from a photo uses a small vision model through **llama.cpp** (`libmtmd`, a GGUF model plus its `mmproj` file), chosen for the **ggml** base it shares with whisper.cpp. That model too is imported by hand and checked with SHA-256 against a list in the app; the app downloads nothing. The candidates, the choice and the native cost follow from S6 (`docs/spikes/S6-handwriting.md`). A shared Settings → *Models* screen for speech and image is proposed after S6.
- **Models are never in a backup** (PO 09-10-2026, see DD-007).

**Alternatives.** Android system recognition (lighter, but not verifiable and not on Windows). Vosk (lighter model, lower accuracy for Dutch — *uncertain*).

**Consequences.** The app stays small (the model is not in it); a one-time import step for the user, which must be in the onboarding and the manual.

**Realises:** REQ-006, REQ-064.

## DD-003 · No sync in v1, but a sync-ready data model ✅

**Context.** On Android *every* socket, LAN traffic included, needs the `INTERNET` permission. *(verified)* LAN sync would therefore lift the hard privacy guarantee of REQ-003. The product owner rejected LAN sync.

**Choice.**
- **No synchronisation in v1** (REQ-007 = Won't).
- **But model sync-ready already now** (REQ-008):
  - UUIDs as primary key, no auto-increment;
  - Hybrid Logical Clock (HLC) per change;
  - tombstones (`deletedAt`) instead of hard deletes;
  - an append-only change log per entity.
- **Implementation in schema v1 (T1.3, 25-09-2026):**
  - UUIDs are **UUIDv7** (sortable by time, own generator in the domain layer, no extra package); HLCs as sortable text `<ms:15>-<counter:4 hex>-<device>`, the device id in the local table `local_state`. The last HLC of this device is read from the change log at start-up, not stored separately: the log is written in the same transaction and so can never lag behind (T1.6).
  - **One clock per device, so one app instance (PO decision 25-09-2026).** Two concurrent Offload processes would share the same device id with each its own `HlcClock`, and then hand out duplicate or non-increasing HLCs. On Windows therefore only one instance may run: a second start brings the existing window to the front (built in T1.6 step B, 27-09-2026: `windows/runner/single_instance.cpp`, a mutex `Local\eu.marandos.offload.single-instance` claimed first thing in `wWinMain`, before the database opens, plus an own window class `eu.marandos.offload.MainWindow` to find the existing window; if claiming fails, the app does not start, because starting would be unsafe; ties in with the keyboard shortcut in T1.7). The mutex applies per Windows session; two concurrent sessions of the same user (e.g. on a terminal server) fall outside it *(accepted: does not occur on the PO's machines)*. On Android there is one process per app. The device id is created with "insert if it does not exist yet" and then read back, so that two concurrent starts also get the same id.
  - **Exception (approved by the PO):** `tokens` are derived data from `items.raw_text` (DD-004). They get no HLC, tombstone or change log and are rebuilt per item; another device derives them itself after synchronisation.
  - **Exception: local tables (approved by the PO 25-09-2026).** `local_state` and the later table of paired devices (DD-013) belong to this one device. They get no HLC, tombstone or change log and never go into a sync package; the pairing key must never leave the device through the log.
  - **Exception: search index (27-09-2026).** The FTS5 index `search_index`, the mapping table `search_map` and the queue `search_pending` are derived, local data, like `tokens`: no HLC, tombstone or change log, never in a sync package, always rebuildable. See DD-016.
  - Tags are attached to items through tokens (`#tag` in the raw text); there is no separate join table.
  - **Always store times in UTC.** Drift stores times as ISO text, with the time zone in it; local times with a changing offset (summer/winter) then sort wrongly in the indexes on `due_at`/`revisit_at`. The repositories (T1.6 onwards) convert every `DateTime` to UTC before writing.
  - **HLC:** the device id consists of ASCII characters (then Dart and SQLite sort the same). `HlcClock.tick()` fails on an impossible system clock; when capturing that must fail visibly, never silently (AC REQ-001).
  - **Points of attention for later:** the unique index on tag names (case-insensitive, only live tags) prevents duplicates on one device, but with future sync two devices can each have their own `#renovatie`; merging has to solve that. `COLLATE NOCASE` only ignores case in the Latin alphabet, not in Cyrillic; with Ukrainian (T8.6) comparing tag and alias names must become Unicode-aware.
  - **Change log replayable on its own (REQ-037, PO decision 25-09-2026):** every log entry contains the full new values of the changed fields, plus a format version. The log never refers to the current database state. This is the basis for manual sync (DD-013); the format must be fixed before T1.6, otherwise a migration of the log follows. Because a row has only one `hlc`, the version per field (needed for last-writer-wins per field, DD-013) comes from the log; the log must therefore not be truncated, unless a version per field is kept.
  - **Format of the change log, version 1 (T1.5b, 25-09-2026):**
    - Every log entry: `entity` (table name), `entity_id`, `hlc`, `operation` (`insert` / `update` / `delete`), `payload` (JSON object) and `format_version` (now `1`).
    - `insert`: all columns of the new row, except `id`, `hlc` and `deleted_at`. `update`: only the columns whose stored value really changes, with the new value; if nothing changes, no HLC and no log entry. `delete`: only `{"deleted_at": …}` (tombstone). `restore`: only `{"deleted_at": null}`, undoing the trash (AC REQ-010; added in T2.3). A new value of the operation is not a format change: existing log entries stay valid.
    - Keys are SQL column names; values are the SQL values as stored (text, integer or null): times as ISO-8601 text in UTC, enum values as their name. `id` and `hlc` are in the log entry, never in the payload.
    - **One write path:** `ChangeLogWriter` (data layer) takes an HLC and writes the row and the log entry in one transaction. It refuses `id`, `hlc` and `deleted_at` from the caller, and times that are not in UTC. Repositories never write directly into a synchronisable table. The log is written in Dart, not with SQLite triggers (recording only changed columns is cumbersome with triggers, and they would have to be off during replay).
    - **Replay:** `ChangeLogReplayer` applies entries in HLC order, in one transaction, with deferred foreign-key checks, and copies them into its own log. It refuses an unknown format version, a table that does not synchronise and column names that are not in the table. Skipping entries already known and last-writer-wins per column belong to sync (DD-013, M9).
    - Schema v1 was changed for this instead of a v2 with a migration: the app did not open the database yet, and no data existed anywhere (approved by the PO 25-09-2026).

- **Deterministic ids (T4.7, PO decision 06-10-2026, SPEC Q33).** The record of a completed time of a recurring task (`item_completions`, DD-018 point 18) gets a **UUIDv5** (SHA-1, RFC 9562) of a fixed namespace and the name `<item id>/<yyyy-mm-dd>`, not a UUIDv7: two devices that complete the same time make the same row, and a double tap or a retry is the same row too. Items keep UUIDv7 (their capture moment is read from the id). The writer gets a method of its own for such an id: insert, or `restore` plus `update` when the row exists as a tombstone. `package:crypto` (already a dependency, pure Dart) gives SHA-1; the generator sits in `lib/domain/ids/` next to UUIDv7.
  - **For M9 (points of attention):** with deterministic ids an insert of a row that already exists is normal. The replayer now does a plain insert and would fail on the primary key; sync must treat it as last-writer-wins per column, `deleted_at := null` included at the insert's HLC, so an undo on one device and a completion again on the other merge right. `items.due_at` of a recurring task depends on the text **and** the records: after an import the app works it out again for every item whose records changed (`processOutdated` only compares tokens with the text). A replayer older than schema v12 refuses the table (version check, as for `item_links.label`).

**Alternatives.** Making it sync-ready afterwards (then needs a migration of all keys and a rewrite of the repository layer).

**Consequences.** A few extra columns and a log table; the change log also gives undo and an audit trail right away. File-based sync (through a folder chosen by the user) stays possible later without a network permission — see the parking lot in SPEC.md.

**Realises:** REQ-007, REQ-008, REQ-037; supports REQ-051 (last touch derived from the HLC) and REQ-057 (append-only journal).

## DD-004 · Hybrid model and extensible inline syntax ✅

**Context.** Input must be frictionless (REQ-018), follow-up structured (REQ-010, REQ-012, REQ-013). The product owner wants to be able to extend the inline syntax later (REQ-028).

**Choice — model.**
- Capturing needs only text. Type and project are assigned in triage. An item without a type is valid and means "not classified yet". The separate type "thought" (SPEC Q10, 25-09-2026) was dropped: a thought is an *idea* (SPEC Q20, PO decision 27-09-2026). Which triage destination yields which type and status is in AC REQ-010.
- Status machine: `inbox → active → waiting → scheduled → done → archived`.
- Triage mode: one card at a time, swipe actions and buttons to six destinations (task, idea, request, waiting for, note, trash; mapping to type and status in AC REQ-010). The exact gestures are decided in the UI design (SPEC Q5b).

**Choice — inline syntax as a token registry.**

1. **The raw text is the source of truth.** `rawText` is always kept unchanged: the app and the parser never change it. Only the user can edit it, in the item detail (DD-018); earlier versions stay in the change log. Recognised tokens are derived metadata with a `parserVersion`. A future parser can therefore parse old items again without data loss.
2. **Registry instead of a hardcoded parser.** Every token type is a definition that registers itself:

```dart
abstract class InlineTokenType {
  String get id;              // 'person', 'tag', 'date', ...
  TokenTrigger get trigger;   // Prefix('@'), Prefix('#'), Prefix('!') or Pattern(...) — see point 3a
  int get schemaVersion;
  TokenMatch? match(String text, int offset, ParseContext ctx);
  Future<ResolvedToken> resolve(TokenMatch m, ResolveContext ctx); // e.g. '@Jan' → person id
  Widget buildChip(ResolvedToken t);                               // live chip below the input field

  // input help (REQ-033, REQ-034)
  String get label;                                                // 'person', 'tag', 'date'
  IconData get icon;
  Future<List<Suggestion>> suggest(String query, ResolveContext ctx);
  String get example;                                              // line for the syntax overview
  void apply(ResolvedToken t, ItemDraft draft);                    // sets a field on the item
}
```

   Adding a new token = registering one new class. The parser core, data model and existing items stay untouched (tokens are stored generically in the `Token` table).
3. **Reserved prefixes** for future use: `^` (project), `~` (duration), `?` (open question), `*` (priority). They are still treated as text for now, but must not be used for anything else. *Since T10.5 (02-10-2026) `^` and `*` are active, see point 11; `~` and `?` stay reserved.* `+` is **not** reserved: international phone numbers start with it (SPEC Q11, PO decision 25-09-2026).
   - **Grammar of `*` (priority):** only a token if `*` is at the start of the text or after white space and directly followed by a fixed value: `*1`/`*2`/`*3` or a language word (`*hoog`/`*laag`, EN `*high`/`*low`, from the ARB files). `* ` (bullet), `*word*` (emphasis) and `**` (bold) stay text, so that Markdown in `body` and notes does not clash. `\*` prevents recognition.
   - **The parser runs on `rawText`,** not on rendered Markdown. When editing in the item detail (T2.3) the same parser recognises the tokens in the edited `rawText`, after saving; the rules for that are in DD-018 point 1.
3a. **Tokens without a prefix (pattern).** A token type has a `TokenTrigger`: either a prefix (`@`, `#`, `!`), or a pattern. Pattern tokens (phone number, email address; REQ-039) are in the syntax overview but not in the prefix bar, and do not open a suggestion list. A pattern token links to the `@person` in the same item; without a person it stays text with a chip "link to…". A phone number saved as a contact detail keeps the text as typed; its E.164 form is derived, never stored (DD-012, PO decision 02-10-2026), and the raw text stays unchanged (point 1).
4. **Escape:** `\@` prevents recognition.
5. **Language-aware:** date words come from the i18n files (`!vr`/`!fri`, `!morgen`/`!tomorrow`); the parser itself contains no language-specific strings.
6. **Unknown = text:** an unrecognised token never produces an error.
7. **Implementation T2.2 step A (27-09-2026; PO decisions 27-09-2026).**
   - **Split over the layers.** The schema above puts `Widget` and `IconData` in the token type; that is not allowed in the domain (pure Dart). Therefore: the domain (`lib/domain/tokens/`) has `InlineTokenType` with `id`, `trigger`, `schemaVersion` and `parse`, plus `InlineTokenRegistry`; chip, icon and label per type are in the presentation layer (`lib/presentation/tokens/token_display.dart`). Resolving against stored data and applying to the item come in step B; `suggest`, `label` and `example` with T2.2a and T2.2b.
   - **Grammar of prefix tokens:** a token starts at the beginning of the text, after white space or directly after an opening bracket `(` `[` `{` (PO decision 27-09-2026, so that `(@Jan)` works) and runs to the next white space; punctuation at the end (`,` `.` `;` `:` `!` `?` and brackets) does not belong to it. Because of this `jan@example.org` is not a person and the escape `\@Jan` works by itself. `@` and `#` must be followed by a letter (any script, Cyrillic included), so that `@10:00` and `#1` stay text.
   - **`@Name` when capturing is only a link** to the person, not *requested by* or *waiting for*; that role is chosen in triage (T2.4).
   - **Date words** (active UI language, from the ARB files, case-insensitive): vandaag, morgen, overmorgen, weekdays short and long, *volgendeweek* (= Monday of next week); EN today, tomorrow, dayafter, nextweek, mon…sun. A weekday is the next such day, never today (`!vr` on a Friday = Friday next week). A date `!dd-mm` is the next one, today included; `!dd-mm-yyyy` as written; a date that does not exist stays text. A date is a calendar date without a time zone (`LocalDate`).
   - **Live chips** below the capture field come purely from the text, without the database (REQ-001).
8. **Implementation T2.2 step B: processing *after* saving (27-09-2026).** `DriftTokenProcessor` (`lib/data/tokens/`, contract `ItemTokenProcessor` in the domain):
   - runs directly after saving without the capture screen waiting for it (hard rule 7), for every widget item pulled in, and once per start for items without tokens of the current `tokenParserVersion` (now 1; candidates chosen in SQL); text without tokens costs no writes, and an item that fails does not hold up the others;
   - relative dates count from the **moment of capture** (from the UUIDv7), not from the processing: `!morgen` from yesterday's widget is today; the date words are those of the language the UI is shown in at that moment (the same source as the screens);
   - people and tags: looked up by name and alias with `nameKey` (Unicode lower case in Dart, not `COLLATE NOCASE`, so that `Олена`/`олена` is one person); unknown → created through `ChangeLogWriter` (DD-015); everything runs one item at a time, so that two items with the same new name give one person;
   - tokens are derived data: replaced per item, without HLC or change log (DD-003); `resolved_value` is the person or tag id, or the date as `yyyy-mm-dd`;
   - **tokens and deadline in one transaction** (review T2.2 step B): the tokens are the "processed" sign, so a deadline that could not be written leaves no tokens either and is still set on the next start;
   - **deadline:** the first date fills `due_at`, only if the item has no deadline yet. ⏳ *Revised for T2.3 (DD-018, PO decision 27-09-2026):* the deadline follows the text; see DD-018 point 1. A deadline without a time is stored as midnight UTC of that date and read back through year, month and day without conversion (`dateOnlyToStored`/`storedToDateOnly`), so that it is the same day in every time zone. ⏳ A real time at 00:00 UTC cannot be told apart from it (SPEC Q24, before the reminders in M4);
   - the raw text never changes through processing (point 1). If processing fails, the next start tries again; no input is lost.
9. **Implementation T2.2a: suggestion list (REQ-033, 27-09-2026; PO decisions 27-09-2026).** `tokenAt` in the registry determines which prefix token you are typing (same boundary rule as recognition); `suggestNames` and `DateVocabulary.suggestions` in the domain make the list, `DriftTokenCandidates` supplies people (with aliases) and tags with the number of linked items. One list for all token types (REQ-028).
   - at most 5 lines; names that start with the input before names that contain it, then the most used, then alphabetically; case-insensitive with Unicode;
   - if the name does not exist yet (not as an alias either) and it is a valid token, the last line is "New: …". Choosing it completes the token; the person or tag only comes into being on saving (step B), never earlier;
   - dates: today, tomorrow, the day after, the coming weekdays by date, next week; because of the limit of 5 lines only the first five are in the list without input, the rest appears when typing (`!vr`, `!vo`); choosing puts the full word in the text (`!vrijdag`); typing `!vr` yourself keeps working;
   - the word you are typing follows the same rules as recognition: punctuation at the end does not belong to it, and if the cursor is behind it (`@Jan.`), there is no list. Choosing replaces only the word: at the end of the text a space follows, elsewhere the rest (bracket, comma, space) stays exactly in place and the cursor comes directly after the word. After choosing, the list stays closed for that token (as after Escape), so that Enter then saves (review T2.2a);
   - a name with spaces goes in as a one-word alias; without such an alias it is not in the list;
   - people and tags are loaded only on the first trigger, asynchronously, once per screen (hard rule 7); a late answer for older text is ignored; saving is always possible, also with a half token;
   - **Windows:** the top line is selected; arrows move, Enter or Tab chooses, Escape closes only the list. When the list is closed, Enter saves. **Android:** tapping chooses; the action key of the keyboard always saves.
10. **Implementation T2.2b: prefix bar and syntax overview (REQ-034, 27-09-2026; PO decisions 27-09-2026).** The bar (`lib/presentation/tokens/prefix_bar.dart`) builds its buttons from the token types with a `PrefixTrigger` in the registry; label, icon and example line come from `tokenLook` (presentation layer, ARB). A new prefix token therefore appears in the bar and the overview by itself; pattern tokens only in the overview (point 3a). If a type has no look of its own in `tokenLook` yet, it appears with the default label and without an example line, never not at all (review T2.2b).
   - tapping puts the sign at the cursor (or over the selection) and puts the focus back in the field, so that the suggestion list opens. If no token can start at that spot (directly after a letter, digit or punctuation mark), a space comes first; that rule is `isTokenStart` in the registry, the same as for recognition;
   - **Android:** the bar is at the bottom, directly above the keyboard. **Windows:** the same bar directly below the text field. The bar and the suggestion list count as a tap in the field (`TextFieldTapRegion`), so that the keyboard stays open;
   - **Collapsed:** one slim line with only the signs (`@ # ! ?`), still tappable, plus a button to expand to sign with label. The expanded state is remembered;
   - the syntax overview shows per token the sign, label and an example line, plus a line about `\` in front (then it stays plain text). On Android a bottom sheet, on Windows a dialog with Close;
   - the setting (Settings → Input: Always visible / Collapsed / Off) and the expanded state are stored per device in `local_state` (never synchronised, DD-003) and read at start-up: quick capture reads nothing from the database when it opens (hard rule 7).

11. **T10.5: `^project` and `*priority` (REQ-050; PO decisions 02-10-2026).** Two token types in the registry (`ProjectTokenType`, `PriorityTokenType`); the parser version goes to 2, so every item is processed once more after the update (point 8).
    - **Project word.** A token is one word, project names often have spaces. The word is compared with the project names by `projectKey`: without case (Unicode, as `nameKey`), spaces, `-`, `_` and trailing punctuation, so `^oudeschuur` and `^Oude-schuur` both name "Oude schuur". `^renovatie/keuken` names the sub-project *Keuken* under *Renovatie*. `^keuken` names the one project in use with that key; when a top-level project shares it with sub-projects, the top-level one; when only sub-projects of different parents share it, none. Archived projects never count. The word starts with a letter or digit (`^2026-plan`), so `2^10` and `^ ` stay text. The suggestion list puts in `wordForProject`: the name with spaces as `-`, or the path when the name alone does not find the project.
    - **Project and the picker.** The project also has its own choice (DD-018 point 1: picker, triage, ⋮). A `^project` therefore does not follow the text like the deadline: it sets the project only when it entered the text (as for a date: the start of the last unbroken run of text versions with the token) *after* the project was last chosen (`projectTokenApplies`). A newly typed token acts like a choice; a later choice in the picker wins over a token that stays in the text; removing the token keeps the project. "Last chosen" is the last change of `context_id` in the change log (not the capture), the processor's own change included, so a token is applied once. "Entered" and "last chosen" are *positions* in the item's change log in HLC order, not clock times, so a tie within one millisecond (possible after sync with clock skew) cannot decide wrongly; the change log is synchronised, so every device decides the same. With several project tokens, the first one in the text that applies sets the project, so an older token never blocks a newly typed one. The decision is taken inside the write transaction, so a choice made in the picker while the item is processed is never overwritten. An older item that was put in a project by hand keeps it after the update. A `^word` that named no project yet counts as never applied: once a project with that name exists, the next processing of the item (an edit, or the processing at start-up) sets it. *Fixed 03-10-2026 (found in use):* the processing at start-up only looked at the parser version and the text, so an item whose project was created (or restored from the archive) after it was processed was never linked; it now also processes items with a project token without a project whose word names one now.
    - **Unknown project.** A name of no project in use sets nothing and creates nothing: it stays a token without a project (`resolved_value` null). A project is only created through "New: create …" in the suggestion list, at the moment it is chosen, as a top-level project (AC REQ-050; PO decision c: if the capture is then cancelled, an empty project stays, visible under Projects and deletable).
    - **Saying so (PO decision 03-10-2026, after use).** Saving with a `^word` of no project used to link nothing without a sign. Asked again whether an unknown `^word` should be created on saving like `@person`, the PO kept the rule above (a token is one word, project names have spaces, typos and half words would become projects, and projects weigh more than tags: Projects, Standstill, weekly review) and chose a visible hint instead. `matchProjectWord` (domain) tells a word that names a project, none (with a name from the word: `-` and `_` as spaces; for `parent/name` under the one existing top-level parent), or several (a sub-project name under different parents). The chip under the text then reads "kas · geen project" or "keuken · meerdere projecten" (calm, DD-017). **Choice — input help (REQ-033, REQ-034).**

A syntax you have to remember is a syntax you do not use. Hence two layers, which solve different problems:

1. **Suggestion list on a trigger.** `@`, `#` or `!` opens a list of at most five suggestions that filters as you keep typing. The content comes from the token type itself (people, tags, or semantic date options). No match means "New: create …", so that you do not have to leave the input field. This helps whoever knows the syntax but not the spelling.
2. **Prefix bar above the keyboard.** Per token a button with sign and label. Tapping inserts the sign and opens the list. This is the actual memory aid: you do not have to *know* that `!` does dates, you see it there. Configurable as *Always visible* (default), *Collapsed* or *Off* — early use asks for visibility, routine for calm.
3. **Syntax overview** behind a `?` button on the right of the bar: all tokens with one example line each. Also shown in the onboarding, but permanently reachable afterwards, because a memory aid that only appears on the first start is no memory aid.

Both layers are **fed by the registry**: every token type supplies its own label, icon, suggestions and example. A new token therefore appears in the list, the bar and the overview by itself. Without that rule every extension would touch three places and so would one day be forgotten — exactly what REQ-028 must prevent.

**Precondition:** the input help must never slow down capturing (REQ-001). The list does not block, saving is possible with a half token, suggestions load asynchronously and the bar is built from static registry data.

**Alternatives.** Fixed form fields (too slow for input). AI classification (unpredictable, large model, not explainable). One monolithic regex parser (hard to extend, breaks with every new syntax).

**Consequences.** A little more initial structure in the parser; every token class can be unit-tested on its own.

**Realises:** REQ-010, REQ-012, REQ-013, REQ-018, REQ-019, REQ-028, REQ-033, REQ-034, REQ-039 (point 12), REQ-050 (point 11), REQ-054 (point 13), REQ-061 (point 14); to be extended for REQ-055 and REQ-056.

## DD-005 · Reminders with inexact alarms ✅

**Context.** Three kinds of reminders are wanted: deadline, "revisit on" and weekly review. From Android 14 `SCHEDULE_EXACT_ALARM` is denied by default for newly installed apps targeting Android 13+; `USE_EXACT_ALARM` is reserved for calendar and alarm-clock apps. *(verified)*

**Choice.**
- **Inexact alarms** with a window of 10 minutes (revised 04-10-2026, SPEC Q38: first at most 5 minutes, but from Android 12 a window is at least 10 minutes). No exact-alarm permission. *Known limit:* in deep sleep (Doze) Android holds an inexact alarm until a maintenance window or until the phone is woken, so a reminder can come later; at the latest when the phone is used (PO accepted 04-10-2026).
- Ask for `POST_NOTIFICATIONS` (Android 13+) only when the first reminder is set. *(common knowledge)*
- "Revisit on" puts the item back to status `inbox` on that date; this is also checked when the app starts (safety net for missed alarms). *Revised 04-10-2026 (T4.2, see below):* the check is the mechanism itself; the notification is only the signal.
- After a device reboot the alarms are scheduled again (`BOOT_COMPLETED`). *Worked out 04-10-2026 (T4.3), see below.*
- **Windows:** reliable as long as the app runs in the system tray. ⏳ Scheduled notifications while the app is fully closed probably need MSIX packaging for an app identity. *(uncertain — architecture agent)* *Decided 04-10-2026 (T4.5), see below: notifications through the tray icon while the app runs; nothing scheduled with Windows.*

**Alternatives.** Exact alarms (extra permission, user friction, Play policy risk) — not needed: a deadline does not have to be on the second.

- **Deadline reminders, decided 04-10-2026 (T4.1; PO decisions after the plan and sketch `16-reminders`, all as proposed):**
  - *A deadline is a date* (SPEC Q24): the reminder comes on that day at the time set in Settings → *Reminders* (NL "Herinneringen"), 09:00 by default; a time in a deadline comes later with a column of its own.
  - *One notification per day*: "3 deadlines vandaag" with the titles below (at most five, then "en nog n"); for one item its title under "Deadline vandaag". *No repeated reminders* for overdue items: they are on *Today*. A tap opens the item, or *Today* when there are more.
  - *Titles* are shown in the notification, but the app never writes them to disk: the planned alarms live in Android's alarm service (memory, gone after a reboot, hence T4.3), the app keeps no copy of their text. (Android's own notification history, when the user turns it on, is outside the app's control.) On the lock screen a public version shows only the count (decision a).
  - *Own platform channel, no package:* `AlarmManager.setWindow` (window 10 minutes) and a receiver that posts the notification, in Kotlin like the other channels. Rejected: `flutter_local_notifications`, which stores every scheduled notification with its text in `SharedPreferences` (plain text on disk, hard rule 2) and ships a native Windows library.
  - *Planning:* pure Dart in `domain/` decides which days get a reminder (open items with a deadline from today, 30 days ahead); `platform/` gets an abstract `ReminderScheduler` (fake for tests) that replaces the whole set at start-up and after every change, which keeps it simple and self-healing.

## DD-006 · Attachments: all file types, encrypted per file ✅

**Context.** All file types must be possible (REQ-023). An encrypted database with unencrypted attachments next to it undermines the whole privacy model.

**Choice.**
- Every file is encrypted separately with **AES-256-GCM**, with a per-file key derived from the master key (DD-007).
  - **Implementation T5.1 step A (09-10-2026; PO decisions 09-10-2026).** *AES-GCM from the platform itself*, no package and no bundled library: Android `javax.crypto` (`AeadChannel.kt`), Windows CNG `bcrypt.dll` through `dart:ffi` (`WindowsAeadCipher`), behind `AeadCipher` in `lib/platform/cipher/` with a fake for tests. Both follow the standard, so what one writes the other reads: proved with the GCM test vectors (test cases 13, 14, 16) and a reference file written by an independent implementation (pyca/cryptography, `test/fixtures/make_attachment_reference.py`), on Windows and the emulator. The PO's condition: nothing may hinder exchange between Android and Windows; a file never travels as is anyway, a backup re-encrypts it (DD-007).
  - **File format v1** (`lib/data/attachments/attachment_format.dart`), streamed in segments, each authenticated on its own (DD-007 "Backup with attachments" point 4, now confirmed): a 32-byte header (`OFA`, version 1, segment size 2^s with s = 16, i.e. **64 KiB** (PO), a 16-byte random salt, a 7-byte random nonce prefix, reserved bytes that must be zero), then the segments, each AES-256-GCM with a 16-byte tag. Nonce = prefix, segment number (4 bytes, big-endian) and a byte that is 1 only for the last segment, so segments cannot be reordered and a file cut short after a segment fails; the associated data is the header plus the attachment id, so a file does not open under another attachment. Per-file key = HKDF-SHA256 of the attachments key (`KeyPurpose.attachments`) with the salt and the id: every file and every rewrite has its own key. Overhead: 16 bytes per 64 KiB (0.02 %, 2.5 kB on 10 MB); one file on disk per attachment.
  - **`AttachmentStore`**: `<app folder>/attachments/<id>` (lower-case id, no extension), written in the folder `attachments/partial/` and moved into place when complete, so the start lists only that small folder, however many attachments there are (REQ-001; PO 11-10-2026, replacing `<id>.partial` next to the files: measured 10-10-2026, listing both folders at start took ≈ 55 ms with 5,000 photos).; reads verify every segment before handing it on; segments go to the cipher 16 at a time (one platform crossing on Android). Measured (debug builds): emulator 50 MB write 4.8 s, read 4.2 s; Windows 1.0 s, 0.9 s; batches of 64 were only about 15 % faster. The CNG calls run on the calling isolate and the Android cipher is a method channel: large transfers belong off the UI isolate, and a background isolate needs `BackgroundIsolateBinaryMessenger` (T7.2b). Transition (11-10-2026): a `<id>.partial` that a version up to 0.6.2 left next to the files or thumbnails goes once per device after the start (`AppStorage.removeOldPartialFiles`, after a capture asked for at start; remembered in `local_state` only when none is left).
  - **Records (T5.1 step B, 09-10-2026).** `DriftAttachmentRepository` writes the file first and then the record through the change log (`insertWithId` with the same UUIDv7, `storagePath` `attachments/<id>`, `sizeBytes` the plaintext size, `pipelineVersion` 0 outside the photo pipeline); a record that cannot be written removes the file again; removing sets the tombstone first, then removes the file. A file orphaned by a crash in between is for T7.4. `AppStorage.open` derives `KeyPurpose.attachments`, knows the folder and removes leftovers in the `partial/` folders of the attachments and the thumbnails (ciphertext only) before anything else. Settings → *Storage* shows *Attachments* (NL "Bijlagen") with the size per kind (photos, audio, other, from the MIME type) and the total, only when there are attachments (PO 09-10-2026).
- **Photos and PDFs**: shown in the app, decrypted in memory.
- **Other files**: only through the explicit action "Open in external app", with a warning. A temporary decrypted copy is made, which is cleaned up on returning to the app and on every start.
- Settings show the storage used per type.
  - **Implementation T7.5 (09-10-2026; PO decisions 09-10-2026), before attachments exist:** Settings → *Storage* (NL "Opslag", below *Backup and export*) shows *Database* ("Encrypted: everything you captured"; the database file with its companion files, `AppStorage.databaseBytes`), *Temporary files* (Android only: the share folder and the document picker's copies, `AppDirectory.temporaryFilesSize`; "A shared backup or export; removed after a day"; Windows keeps none, so no row) and *Content* ("2 items, 1 of them in the trash · 8 projects · 15 people": every item with the trash, as it is still in the database; projects with the archived ones; people without the merged ones; `readStorageCounts`). Sizes in decimal kB/MB/GB as Android shows them (`byteAmount`). Worked out each time Settings opens, not in the background; no button to clear the temporary files, they go by themselves (PO). The attachments per type and the speech model add their own row when they are built (T5.1, T6.1).
- **Owner of an attachment** is an item or a person (business card, REQ-041). Both use the same storage, encryption and photo pipeline. The database enforces that exactly one of `item_id` and `person_id` is filled (T1.5b).

### Photo pipeline (taken from `photo-resize-port-spec.md`, D1–D9)

One `PhotoStorageService` does compressing, making thumbnails, deriving paths and deleting.

| Source | Decision | Adoption |
|---|---|---|
| D1 | **display** ≤ 1600 px longest side, JPEG q ≈ 82; **thumbnail** ≤ 256 px, q ≈ 75; keep no original | Adopted; see open point Q7 |
| D2 | Same pipeline for every photo type | Trivial: there is one entity with a photo path (Attachment) |
| D3 | No schema column for the thumbnail; derive the path by convention | Adopted: the display version is the attachment itself, `attachments/<attachmentId>` (T5.1); the thumbnail is `attachments/thumbs/<attachmentId>` (*T5.2, PO 10-10-2026*: inside the attachments folder, so it moves and goes with it on a restore). The column `thumbnail path` from v0.1 was removed |
| D4 | Apply rotation, strip EXIF | Adopted; ties in with REQ-024 (GPS removed) |
| D5 | `flutter_image_compress` | **Replaced** (does not cover Windows, REQ-009). Decision after spike S2 (24-09-2026): the **Flutter engine codec** (`dart:ui` `instantiateImageCodec` with a target size) decodes, applies the EXIF orientation and downscales; **`package:image`** (pure Dart) only encodes the downscaled result to JPEG. No native code, no plugin. `image_compress_plus` (crash in the Windows release build, no orientation on Android) and `ironpress` (no orientation) were rejected. See `docs/spikes/S2-image-compress.md` |
| D6 | One-time migration of existing photos | **Not applicable:** greenfield. Instead every attachment gets a `pipelineVersion`, so that a later recompression pass (run-once guard, progress, skip-on-error) stays possible |
| D7 | Backup contains only display versions; thumbnails regenerated on restore | Adopted; fits within the encrypted backup of DD-007 and the option "with or without attachments" |
| D8 | Deleting or replacing cleans up both files | Adopted; there is no existing clean-up pattern yet, so this becomes the pattern |
| D9 | Missing thumbnail → fall back to display, regenerate lazily | Adopted (REQ-032) |

**Adjustments for *this* codebase:**

1. **Encryption (deviation from the source spec).** Spirit Safe writes plain files; here every attachment is encrypted. Therefore: compress in memory (engine codec + `package:image`, see D5) and only then write encrypted. Lazy regeneration (D9) therefore first needs decrypting the display version. "Verifying" here means decrypting and decoding, not just checking the file size.
2. **File names.** The derived convention uses the `attachmentId`, not the original file name with `.jpg`: encrypted files have no meaningful extension.
3. **Size (Q7).** The source spec explicitly names a desktop target (D1) and photo types that must be readable like documents (D2) as a *revisit trigger*. Both apply here: Windows screens and whiteboard or diagram photos. The values are therefore in one `ImagePolicy` object; start at 1600/256 and raise to 2048 if handwriting turns out to be unreadable.
4. **The screen stays smooth while a photo is processed** (tightened after S2; the source spec said "outside the UI isolate"). The heavy work (decoding, downscaling) runs natively on engine threads, the JPEG encoding in an `Isolate.run`; the call itself may start in the UI isolate. **Measurable:** no extra frame pauses while processing a 50 MP photo.
5. **Caching and decode size when rendering.** The original complaint in Spirit Safe was the *loading time* of thumbnails, not the storage space: a 4000×3000 JPEG decodes to roughly a 48 MB bitmap, per list row. Encryption adds a decryption step per render here, so without caching every scroll decodes *and* decrypts again. Therefore:
   - an own `ImageProvider` with the `attachmentId` (plus variant: display or thumbnail) as the **cache key**. A fresh `MemoryImage` per render bypasses Flutter's `ImageCache` completely — then the gain of the thumbnail never arrives;
   - pass `cacheWidth` / `cacheHeight` when decoding, so that the bitmap lands in memory at display size instead of file size;
   - do not hold on to decrypted bytes longer than the decode step needs.

   **Measurable:** scrolling through a list of ≥ 100 items with a photo stays at 60 fps, without jank frames while loading.

6. **As built (T5.2, 10-10-2026; PO decisions a–e):** `ImagePolicy` and `decodeTarget` in `lib/domain/attachments/image_policy.dart` (`photoPipelineVersion` 1); `PhotoCompressor` (`lib/data/attachments/photo_compressor.dart`) reads the stored size and EXIF orientation of a JPEG from its headers (other formats: the platform's `ImageDescriptor`, upright), lets the engine codec decode to the upright long side and encodes in an `Isolate.run`; the thumbnail is made **from the display version**, not from the original (faster, and the same path as the regeneration of D9). `PhotoStorageService` writes the thumbnail first, then the display version with its record (`DriftAttachmentRepository.add` with an id from `newId`), and on failure removes both; `thumbnail(id)` makes a missing or damaged thumbnail again and keeps it; `delete` removes the record and the display version, then the thumbnail (D8). **Variant binding (review T5.1, PO b):** `AttachmentVariant.thumbnail` goes into the per-file key (HKDF info `…/v1/thumbnail/<id>`) and the associated data, so a display version never opens as a thumbnail or the reverse; the display version keeps the binding of T5.1, so no format version and no migration. A write stopped halfway in `thumbs/` is cleared at start like the others. Formats: JPEG with orientation; PNG and WebP through the engine; what the platform cannot decode throws `PhotoFormatException` (a message in T5.3); HEIC is not handled separately (PO e). **Measured (profile, the two real 50 MP photos of S2, both files):** Windows ≈ 0.95 s per photo, of which the thumbnail ≈ 35 ms, largest frame gap 9 ms; Android emulator ≈ 1.5 s, thumbnail ≈ 60 ms, frame gap 66 ms (emulator baseline ≈ 50 ms); display 254–400 KB, thumbnail 10–12 KB. The own device follows (PO: Monday 12-10-2026, with S6).

**Acceptance:** see AC REQ-024 / REQ-027 / REQ-032 in SPEC.md. Tests cover sizes, orientation, path derivation and "delete both".

**Alternatives.** Attachments in the database as BLOBs (makes the database big and backups slow). Allow only text and photos (rejected by the product owner).

**Consequences.** Decrypted data only leaves the app's domain through a deliberate action: "Open in external app" here, and further export (DD-007) and sharing (DD-014); see hard rule 2 in `CLAUDE.md`.

**Realises:** REQ-023, REQ-024, REQ-025, REQ-027, REQ-032, REQ-041, REQ-044.

## DD-007 · Key management without an app lock; backup with a passphrase ✅

**Context.** The product owner finds biometrics or an app lock unnecessary. Encryption is still required (REQ-004).

**Choice.**
- The **master key** is generated at random on the first start and stored in the **Android Keystore** or **Windows DPAPI** respectively. When the app opens, it is unlocked automatically; there is no prompt.
  - **Implementation (PO decision 25-09-2026, T1.4):** an own thin `KeyStore` in `platform/` (Android: Keystore through a platform channel; Windows: DPAPI through `dart:ffi`), without `flutter_secure_storage`. Reason: fewer dependencies and less native code in the release gate (DD-008). *(How much that package brings along was not measured; uncertain.)*
  - **Storage model:** a Keystore key cannot be exported, but HKDF needs the raw bytes. Therefore the master key is 32 random bytes, stored as a *wrapped* file: on Android encrypted with an AES-GCM key that stays in the Keystore, on Windows as a DPAPI blob (bound to the user account). Where these documents say "device key", the master key or a key derived from it is meant.
  - **Keys per purpose:** the master key is never used directly. Per purpose an own key is derived with HKDF-SHA256 and a fixed label: first only the database; later a key for attachments and a key with which the backup key (Argon2id) and the pairing keys (DD-013) are stored encrypted on the device. A new purpose therefore needs no new master key.
  - **Exception: the widget queue (PO decision 27-09-2026, T1.7).** The encrypted queue between the native input window and the app (DD-010) has its own non-exportable AES-256-GCM key in the Android Keystore (`offload_capture_queue_v1`), not derived from the master key. Reason: the input window then never has to unwrap the master key; it stays small and fast (REQ-001), and the master key is in memory nowhere outside the app. The queue only holds items that are not in the database yet and is emptied after saving. Like the master key, this key is not included in a backup (`allowBackup="false"`).
  - **Never lose data:** if the database exists but the key is missing, a clear error follows. The app then never creates a new key and overwrites nothing. Android system backup and device-to-device transfer are off (`allowBackup="false"` plus `dataExtractionRules` that exclude everything for `cloud-backup` *and* `device-transfer`; since Android 12 `allowBackup` alone is not enough): a transferred database without the matching Keystore key is unreadable. Transferring goes through the app's own backup (REQ-014).
  - **Measured in T1.4 (25-09-2026):** SQLite3MultipleCiphers 2.5.0 accepts the raw 256-bit key (`PRAGMA key = "x'…'"`) with `chacha20`, without a passphrase KDF (opening ~6 ms against ~33 ms). The file does not record the cipher: with another cipher it does not open, so `PRAGMA cipher = 'chacha20'` on every connection is needed. FTS5 is in the build (REQ-011) and the `-wal` file is encrypted too. HKDF comes from `package:crypto` (Dart team, was already in the app transitively; approved by the PO). Windows key file: `%LOCALAPPDATA%\eu.marandos.offload\master_key.key`; Android: `noBackupFilesDir/master_key.key`.
  - **Start-up (T1.6 step A, 25-09-2026):** the database is `offload.db` in the app's own folder: Android `filesDir` (through an own channel, no `path_provider`), Windows `%LOCALAPPDATA%\eu.marandos.offload`. "There is data" means: that file exists. Then a missing key gives an error screen and never a new key. The error screen distinguishes a missing key, an unreadable key and a database that does not open, offers only "Try again" and changes or deletes nothing.
- **Database encryption** through SQLite3MultipleCiphers (Drift ≥ 2.32, sqlite3 3.x). Enable it right from version 1: `pragma key` cannot simply be applied to an existing database. *(verified)*
- **Protects against:** access at file level (disk image, loose backup files, other Windows accounts — DPAPI is bound to the user account).
- **Deliberately accepted:** whoever holds the unlocked device sees everything. The device lock is the gatekeeper.
- **Backup (REQ-014, REQ-026):**
  - The device key cannot be exported; backups are therefore encrypted with a **passphrase chosen by the user** through **Argon2id**.
  - Set and change through **Settings → Backup**: entered twice, strength indicator, minimum length, and an explicitly confirmed warning that a forgotten passphrase cannot be recovered.
  - To make **automatic backups** possible, the passphrase (or better: the key derived from it) is stored on the device, itself encrypted with the device key. Restoring on another device always asks for the passphrase again.
  - Changing the passphrase applies to new backups; the UI says that older backups keep the old passphrase.
  - Backup options: with or without attachments.
  - **Models are never in a backup (PO 09-10-2026).** The speech model (DD-002) and the vision model (REQ-064) are large and can be imported again; a backup, also one with attachments, never includes them. After a restore the app says which model has to be imported again. Their size is a row of its own in Settings → *Storage* (T7.5).
  - **Implementation decided 03-10-2026 (T7.1, T7.2; PO decisions after a spike).** No new package: SQLite3MultipleCiphers, which already encrypts the database, also makes the backup. Its **AEGIS** cipher derives the key from a passphrase with **Argon2id** built in. *Making:* a second connection to the database (opened with URI filenames) runs `VACUUM INTO 'file:…?cipher=aegis&key=…'`, so the copy is written encrypted from the first byte; then the copy's `local_state` (device-local, never synchronised, DD-003) is emptied, so a backup holds no device settings and no passphrase. Measured on Windows (spike): 43 ms for a small database, opening with the passphrase 39 ms; without the passphrase the file is unreadable and holds no readable text. *Restoring:* the chosen file is copied into the app's own folder (still encrypted), opened with the passphrase, checked (a schema newer than the app's is refused; an older one is migrated as at start-up), and turned into a database of this device by switching its cipher and key (`PRAGMA cipher = 'chacha20'` plus `PRAGMA rekey` with the raw device key); only after the user confirms does it replace `offload.db`, and the previous file is kept, encrypted, until the restored one has opened. **Argon2id strength (PO):** 64 MiB and 3 passes when that stays under one second on a phone, otherwise the library default (19 MiB, 2 passes, the OWASP minimum); measured in step A. **Passphrase (PO):** set once in Settings → Backup, at least 12 characters, a simple strength indicator on length and variety (no package), stored in this device's `local_state` (inside the encrypted database, so encrypted with the device key, as above). *Restoring (PO 03-10-2026):* the stored passphrase is tried first, so restoring on the same device asks nothing; it is asked only when it does not open the file (a backup from another device, or from before a change of passphrase). Restoring is always confirmed, as it replaces everything.
  - **Implementation step A (03-10-2026, no visible change yet):** `lib/domain/backup/backup.dart` (`minPassphraseLength`, `passphraseStrength`, `BackupProblem`, `BackupInfo`); `lib/data/backup/backup_files.dart` (`BackupFiles.write`, `inspect`, `prepareRestore`, each in an isolate of its own; the settings of Argon2id are not recorded in the file, so `backupKdfs` lists them, the current first, and opening tries each); `AppStorage` keeps the passphrase (`saveBackupPassphrase`, `hasBackupPassphrase`), makes the backup (`makeBackup`), prepares a restore next to the database (`offload.restore.db`, this device's own passphrase tried first), swaps it in once the storage is closed (`finishRestore`, the previous database kept as `offload.before-restore.db` until the restored one opens), puts it back (`undoRestore`) and, at start, finishes a swap that was stopped halfway or drops a restore never swapped in. Measured (`integration_test/backup_test.dart`, 200 items, 64 MiB and 3 passes): emulator 1.4 s to make, 0.25 s to open, 0.5 s to restore; Windows 0.4, 0.2 and 0.4 s. A phone is slower than the emulator; the PO reports the time on the own phone after step C, and the settings go back to the library default if it is over a second per opening. *From the review of step A:* the database runs with a rollback journal, not WAL, so every connection now waits up to 10 seconds for a lock (`busy_timeout` in `applyEncryption`) instead of failing at once: a capture during a backup waits for the copy rather than failing; the copy reads through a read-only connection; a failed backup or restore copy leaves no file, and the journal of each file is moved or removed with it. *For M9:* after a restore the device has a new id without HLCs of its own, so its clock starts from the wall clock; if the source device's clock ran ahead, its first edits sort before the restored ones. Seeding the clock from the newest HLC in the change log (a "receive") is noted at T9.3.
  - **Implementation steps B and C (03-10-2026, 0.3.18):** `BackupFilePicker` in `lib/platform/backup_file/`: on Android the system document picker (`BackupFileChannel.kt`: `ACTION_CREATE_DOCUMENT`/`ACTION_OPEN_DOCUMENT`, no permission; the bytes of the already encrypted file are copied between the chosen document and a copy in the app's own cache, which is removed right after), on Windows the runner's Save as and a new Open window (`save_dialog.cpp`), the chosen path used directly. Settings → **Backup** (NL "Back-up", at the end of Settings): *Passphrase* (NL "Wachtwoordzin"; dialog: twice, at least 12 characters, strength, the warning to confirm, on a change the note about older backups), *Make a backup* (NL "Back-up maken"; asks the passphrase first when none is set; file name `Offload-backup-<date>.offload`, NL `Offload-back-up-<date>.offload`), *Restore a backup* (NL "Back-up terugzetten"; choose the file; this device's own passphrase first, otherwise asked; a confirmation with the number of items and the newest change; then the storage closes, the restore is swapped in and the app opens again through the start-up screen). `AppStorage.close` is idempotent, and `open` puts the previous database back by itself when a restored one does not open. **Restore and this device (PO, SPEC Q15):** the data comes from the backup, this device keeps its own `local_state` (language, country for phone numbers, prefix bar, passphrase) and gets a **new device id**, so two devices never share an HLC node; pairings (M9) do not exist yet. **Restore is a copy, not a sync:** it replaces everything on the target device; keeping two devices in step is M9. The file is saved and opened through the system dialogs (Android: the document picker, no permission; Windows: Save as and Open), name `Offload-back-up-<date>.offload`; the app never connects anywhere. Passphrases go into SQL and URI text escaped, and errors never echo the statement (as for `PRAGMA key`).
  - **Sharing a backup on Android (T7.2a, PO decisions 09-10-2026):** on Android *Make a backup* first opens a sheet with *Share…* (NL "Delen…") and *Save on this device…* (NL "Opslaan op dit toestel…", the document picker as before); Windows is unchanged (Save as). *Share…* writes the encrypted backup straight into the share folder of the app's cache and hands it to the Android share menu through `ShareChannel.shareFile` (DD-014), as `application/octet-stream` with the file name as subject. The message is "Backup ready to share" (NL "Back-up klaargezet om te delen"): Android does not say whether it was really sent. The shared file is always encrypted, so it may stay in the cache for a while (SPEC Q12).
  - **Backup with attachments (T7.2b) — designed by the architecture agent and decided by the PO, 09-10-2026 (points 1–7, all as advised).** *Why now (PO 09-10-2026):* once there are recordings (T6.2), a backup without attachments misses audio that is not, or badly, transcribed, while the audio is the source (DD-002). So T7.2b comes right after T5.1 and before T6.2.
    1. **One file, as now.** The attachments go *inside* the backup file: a table that exists only in the backup copy, `backup_attachment_chunks(attachment_id, seq, data BLOB, PRIMARY KEY (attachment_id, seq))`, plus `backup_meta` (format version, whether attachments are included) and `backup_attachments` (per attachment its plaintext size and SHA-256; *as built in T7.2b step A*). AEGIS with Argon2id encrypts these pages like every other page, so the backup stays one file, encrypted with the passphrase, and *sharing* (T7.2a), *saving* and *restoring* keep their flow. This differs from the alternative rejected in DD-006 (BLOBs in the *live* database): the live database stays small; only the backup copy carries the bytes.
    2. **Making.** After `VACUUM INTO` (as now), in the same background isolate: per attachment record that is not deleted (no tombstone; *as built:* also the attachments of an item in the trash, which the copy holds and which can come back), `AttachmentStore` (T5.1) decrypts the file with the device's attachment key (HKDF from the master key) **as a stream**, and every piece goes straight into a chunk row (1 MiB). Plaintext exists only in memory, one chunk at a time, and in the AEGIS-encrypted pages; **never unencrypted on disk** (hard rule 2). Photos only as display versions; thumbnails are not included and are made again on restore (DD-006/D7, with M5). A record whose file is missing or does not verify: the backup is still made, without that file, and says so ("n attachments were missing"); cleaning up orphans is T7.4.
    3. **Restoring: all or nothing.** *As built (T7.2b step B, 09-10-2026):* the old folder becomes `attachments.before-restore/` in `finishRestore`; for a backup without attachments a keep list (`attachments.keep`) names this device's files of restored records (7c, option b), and those move over only once the restored database has opened, so an undo puts the old folder back whole; the restored copy is vacuumed after the chunk tables are dropped. `prepareRestore` (as now: check the passphrase, copy rekeyed to the device key) also reads the chunks of every attachment, checks size and SHA-256, and writes it with *this* device's attachment key into a staging folder next to the attachments folder (`attachments.restore/`). Then the chunk tables are dropped from the restore copy and it is vacuumed, so the restored database is no larger than it should be. `finishRestore` swaps the database and the attachments folder together, keeping the previous ones (`attachments.before-restore/`) until the restored database has opened, exactly as for the database now; an interruption is finished or rolled back at the next start. *Undo (T7.2b step C, review):* when the restored database does not open, `undoRestore` first removes it, then puts the folder from before back, then the database from before; stopped after any step, the next start finds no database and runs it again. (Putting the database back first would leave the folder from before beside it, which a start takes for a committed restore and removes.) Any failure before the swap leaves everything as it was and removes the staging folder.
    4. **Memory.** Never a whole file in memory: decrypting, writing chunk rows, reading them back and encrypting all go per chunk. *Requirement on T5.1 (PO 09-10-2026: accepted as the starting point of its design):* `AttachmentStore` reads and writes as a stream, in segments that are each authenticated on their own (AES-256-GCM per segment, nonce from a file nonce and the segment number, the last segment marked), so no unverified plaintext is passed on and a large recording needs no large buffer. *(To be confirmed when T5.1 is designed; one GCM tag over a whole file would force either buffering the whole file or passing on unverified bytes.)*
    5. **Size and the share copy.** A backup grows with the attachments (a recording is in the order of 1 MB per minute, depending on the format chosen in T6.2; photos about 0.3–0.6 MB each at 1600 px). Before making, Offload compares the expected size (database plus attachments) with the free space and refuses with a message rather than fail halfway. On Android the copy for *Share…* (`cache/share/`, T7.2a) and the copy for the document picker then take that space for a while; the share copy follows the 24-hour rule (SPEC Q12), the picker copy is removed right after. Making and restoring show progress ("12 of 85 MB") when there is more than a few MB. *As built (T7.2b step C, 10-10-2026; PO: the check also before restoring):* the room needed is `roomNeeded` (`lib/domain/backup/backup.dart`: the bytes, a tenth more and 16 MiB), for making the database plus the attachments chosen, checked on the folder the file is written to (on Android the copy in the app's cache), for restoring twice the backup file (the rekeyed copy and the re-encrypted attachments), checked on the app's folder; the free space comes from `AppDirectory.freeBytes` (Android `StatFs.availableBytes`, Windows `GetDiskFreeSpaceExW`), and when the platform cannot tell, Offload goes on. The bar with sizes shows from a total of 4 MiB; below it the usual "one moment".
    6. **Version.** `backup_meta.format_version` starts at 1; restoring refuses a higher one with the existing "made with a newer version of Offload" message. An app from before T7.2b only checks `PRAGMA user_version`; T5.1 is expected to raise the schema version (attachment columns), so a backup that carries attachments is refused by an older app instead of being restored without its files. *(Check when T5.1 is built; if T5.1 does not raise it, raise the schema version with T7.2b on purpose.)*
    7. **Decided by the PO (09-10-2026), all as advised.**
       - **(a) With or without attachments (REQ-014):** when making a backup, a switch "With attachments (≈ size)" (NL "Met bijlagen (≈ …)"), where the size is the actual total of the attachments on this device at that moment (e.g. "≈ 85 MB" or "≈ 3 MB"), so the cost in time and space is visible; on by default and shown only when there are attachments; Windows the same. Without them, the attachment records stay in the backup and their items show "Attachment not in this backup" (NL "Bijlage niet in deze back-up") after a restore, so nothing disappears silently; the transcription text (T6.3) is in the database either way.
       - **(b) Settings → Storage:** the row *Attachments* (from T5.1) is enough; no separate "expected backup size" row, as the switch shows it when it matters.
       - **(c) Restore of a backup without attachments onto a device that has attachments** — *revised by the PO 09-10-2026 (T7.2b, option b; first decided "all gone"):* the device keeps its own attachment files that belong to a record in the restored database: they are encrypted with this device's key, so they still open, and every read verifies them. Files without such a record go. Restoring your own backup made without attachments on the same device therefore loses nothing; on another device the result is the same as before (no files). Still all or nothing: *as built (T7.2b step B)* the kept files are listed when the restore is prepared and move into the new attachments folder once the restored database has opened — the commit point after which nothing is rolled back (review); a failure while moving them fails that start and the next start finishes it. The restore confirmation says so explicitly ("This backup has no attachments; attachments that do not belong to the restored items will be gone"). A backup *with* attachments replaces the folder entirely, as decided.
       - **(d) Progress and cancelling:** progress yes; no cancel button in v1 (a failed backup removes its half file anyway).
       - **(e)** The streaming, per-segment authenticated `AttachmentStore` (point 4) is the starting point of the design of T5.1.
- **Export** (Markdown/JSON) is unencrypted and is therefore offered as an explicit action with a warning.
  - **Implementation T7.3 (09-10-2026; PO decisions 09-10-2026, AC REQ-014):** Settings → *Backup and export* (NL "Back-up en export", the section renamed) → *Export* (NL "Exporteren"; "Readable, not encrypted (Markdown or JSON)", NL "Leesbaar, niet versleuteld (Markdown of JSON)"). A dialog shows the warning ("This export is not encrypted. Anyone with the file can read everything.", NL "Deze export is niet versleuteld. Iedereen met het bestand kan alles lezen.") and the choice Markdown/JSON; *Export* confirms, every time. Then, as for a backup, the Android sheet (*Share…* / *Save on this device…*) or *Save as* on Windows; messages "Export saved" (NL "Export opgeslagen"), "Export ready to share" (NL "Export klaargezet om te delen"), "The export did not work" (NL "De export is niet gelukt"). `DriftExportRepository` reads in one transaction everything outside the trash, and the **merged people** (tombstoned by the merge, but an item restored from the trash or from a sync may still name one; review): `ExportData` with items, projects, people with `mergedIntoId`, contact details, links (with their kind), completions and notes; links, completions and notes of something in the trash are left out. ## DD-008 · Network-free build, demonstrably 🔍

**Context.** The privacy promise must be verifiable, not just promised (REQ-003, REQ-015).

**Choice.**
- The release manifest contains **no** `android.permission.INTERNET`.
- Note: Flutter adds this permission by default to the *debug* and *profile* manifests (needed for hot reload). *(common knowledge)* The check therefore applies specifically to the **merged release manifest**.
- **Release check (T1.2):** `tool/check_permissions.sh` reads the permissions from the release APK with `aapt2 dump permissions` and fails on every permission that is not in `tool/allowed_permissions.txt`. `INTERNET` and the exact-alarm permissions may never be in it (the script refuses that). This also covers "no new permission", not only `INTERNET`.
- **Dependency policy:** no analytics, crash-reporting or advertising SDKs. Every new dependency is checked for manifest permissions, network use and native code. Enforced by `tool/check_dependencies.sh`: all Dart packages that end up in the app (indirect ones too, without dev dependencies) must be in `tool/allowed_packages.txt`, and all native code (`.so` in the APK; every `.dll` and `.exe` in the Windows bundle, also in subfolders) in `tool/allowed_native_libs.txt`. The comparison is by file name. An addition needs approval from the product owner; the `architecture-reviewer` (role of architecture agent) sees every change to those lists. As an illustration: adding just `path_provider` brings 29 packages and `libdartjni.so`.
- **The APK is the reference.** Offload is installed as an APK; if distribution ever goes through an AAB, a check on the bundle's manifest follows (`bundletool`). Both scripts fail when in doubt (unreadable `aapt2` output, a missing Windows build unless explicitly `SKIP_WINDOWS=1`) and only give something meaningful after a fresh release build.
- **CI:** while the repo is local, these scripts are the gate (Definition of Done). A GitHub Actions workflow follows on publication (backlog T8.7).
- **Native SQLite library (decision T1.1, 24-09-2026):** SQLite3MultipleCiphers comes as a **ready-made download** through the build hook of `sqlite3` (default), checked against the sha256 hashes in the package source; provenance (SLSA/SBOM) is available. Building therefore needs internet; the app itself stays network-free. Fallback for offline or reproducible builds: `source: source` with an own amalgamation (see `docs/spikes/S1-encrypted-db.md`).
- **Windows:** no network code in the app; verifiable through the dependency review. A firewall rule is up to the user.

- **Version and build moment (REQ-060, T1.8, 27-09-2026).** Without an extra package (`package_info_plus` is a plugin with native code): `tool/build_release.dart apk|windows` writes the version from `pubspec.yaml`, the build number and the build moment in UTC to `build/build_info.json` and then runs `flutter build … --release --build-number=<n> --dart-define-from-file=build/build_info.json`, which bakes them into the app as constants (`BuildInfo` in `lib/domain/app/`). If they are missing, Settings shows "Development build". Because one script does both steps, a release can no longer get an old build moment (review T1.8). No git commit in the app (PO decision 27-09-2026).
- **Build number = number of commits (28-09-2026).** `git rev-list --count HEAD`: always rising, so Android accepts the APK as an update over an existing installation, and traceable to a commit. The number in `pubspec.yaml` (`+1`) now only applies to development builds. Rejected: `yyMMddNN` (e.g. `26092701`): readable, but it does not fit in the Windows version information of the exe, where each of the four fields is 16 bits (max. 65535, `FILEVERSION` in `windows/runner/Runner.rc`); the script refuses a number above 65535. A build with uncommitted changes gets the number of `HEAD` and a warning; copies for use come from a clean tree (PO decision 28-09-2026). The count is only right over the full history: the script refuses a shallow clone (e.g. a CI checkout with `depth 1`), and rewritten history can lower the number (hence no `rebase` etc. without the PO, see the commit gate). For the APK the script first stops the Gradle daemon and afterwards checks that the output file was really written by this build (pitfall in `CLAUDE.md`); for Windows that is `data/app.so`, because the exe is only relinked when the runner or the build number changes.
  - **Fresh history (11-10-2026, PO decision, SPEC Q28):** the repository was restarted with one commit for publication (the content of the private history's last commit, tree `7883e02`); the private history (260 commits) is kept locally. So the number is now `buildNumberBase` (260, `tool/build_release.dart`) plus the commit count: it stays above every APK built before, so Android keeps accepting updates (a lower `versionCode` is refused, and an uninstall loses the database and the Keystore keys), and the release copy folders (`<version>+<n>/`) cannot collide with old ones. The base is never lowered.
- **Release copies (28-09-2026, PO decision):** `--copy` copies a build to a folder per build (`<version>+<n>/`, with `Offload-<version>+<n>.apk` or `Offload-<version>+<n>-windows/`) under the directory in the local environment variable `OFFLOAD_RELEASE_DIR`; the path is a setting of the PO's machine, never in the repository. Only from a clean tree (the number then names a commit), checked before building; an existing copy is never overwritten and every copied file is compared byte for byte. The copy is written under a temporary `.partial` name and renamed when complete, so a failed copy never looks finished; a failed copy removes what it wrote. The PO decides per tested release build whether it is copied.
- **Version name 0.M.y (28-09-2026, PO decision).** The version name in `pubspec.yaml` says how far the app is; the build number (commit count) stays the unique, rising number. Until v1 the name is `0.<milestone>.<tasks>`: the middle number is the milestone in progress (M2 → `0.2.y`), the last number counts the tasks finished in that milestone and goes back to 0 when the next milestone starts. When M8 is done, v1 is `1.0.0`. Fixes do not raise the name: the build number already tells builds apart, and a fix is listed under *Fixed* in the next version of `CHANGELOG.md`. Raising goes through a small script (`tool/bump_version.dart task|milestone`, T1.10) in the commit that finishes the task; it also turns `[Unreleased]` in the CHANGELOG into `[<version>] – <date>`. Start value: `0.2.9` (nine tasks of M2 done on 28-09-2026). Rejected: `1.0.0` right away (the name would suggest that v1, the scope in `BACKLOG.md`, is done); deriving `y` from the ticked boxes in `BACKLOG.md` (depends on parsing Markdown, and CHANGELOG headings would stay manual work); raising only per release copy (then `y` says nothing about progress). The name change does not affect Android updates (`versionCode` = build number) or the Windows `FILEVERSION` (16 bits per field). Refined 29-09-2026 (PO): only tasks with a user-visible change raise the name (tooling such as T1.10 does not); the commit that finishes the last task of a milestone runs `milestone` instead of `task`, so its entries land under `[0.<M+1>.0]` and no empty heading follows; the script refuses anything but `0.M.y`, so what comes after `1.0.0` is decided with the PO. The first run set `pubspec.yaml` to `0.2.8` and raised it to `0.2.9`, which turned the changes so far into `[0.2.9]`.

## DD-010 · Input channels per platform behind one abstraction 🔍

**Context.** Android has a widget and a share menu; Windows has a keyboard shortcut and a system tray. The rest of the app must not know about any of this.

**Choice.**

```dart
abstract class CaptureChannel {
  Stream<CaptureEvent> get events;   // text, shared content, audio, source
}
```

| Platform | Implementations |
|---|---|
| Android | Home-screen widget (opens a minimal input screen with direct focus), share target for text/URL (files: T5.8), shortcut for voice |
| Windows | Global keyboard shortcut `Win+Shift+B` brings the main window to the front with the capture screen (making it configurable: T8.8); system-tray icon with "New item" (see the implementation below) |

- All channels deliver the same `CaptureEvent`; the use case `CaptureItem` handles them identically (inline parsing, recording the source, status `inbox`).
- **Implementation Android widget (T1.7 step A, 27-09-2026; spike S3 variant A).** A stream does not fit the requirement that a confirmed item is never lost (AC REQ-001): the app must store first and only then let it be deleted. Therefore `CaptureChannel` (in `lib/platform/capture/`) is a queue with two steps: `pending()` returns the waiting items without deleting anything, `acknowledge(ids)` deletes them after the app has stored them. The schema above stays the intent; for the Windows keyboard shortcut (step B) a signal "open the input screen" is added.
  - The native window (`QuickCaptureActivity`, Kotlin, without Flutter) puts the text in an encrypted queue (`CaptureQueue`, `files/capture_queue/`): write, `fsync`, rename, folder `fsync`; only then does the window close. Unreadable files go to `quarantine/`, never away; the app reports them in the inbox.
  - Every item gets a UUIDv7 at the tap. The app stores it under that id (`insertWithId`); that way the time in the inbox is the moment of the tap, and an item that comes in twice is stored once.
  - The app empties the queue on start and every time it returns.
  - The texts of the window and the widget come from the ARB files (`tool/gen_android_strings.dart`) and follow the system language, with English as the fallback (PO decision 27-09-2026).
  - Before the first unlock after a reboot the widget does not work: the queue is in encrypted user storage *(not tested, see S3)*.
- **Implementation Windows (T1.7 step B, 27-09-2026; PO decisions 27-09-2026).** `windows/runner/windows_shell.cpp` in the runner, through the channel `eu.marandos.offload/windows_shell` (in Dart: `WindowsCaptureChannel` and `DesktopShell`):
  - **Keyboard shortcut `Win+Shift+B`** (`RegisterHotKey`). If the combination already belongs to another program, the inbox says so; never silently. Making it configurable is a later item (T8.8).
  - No separate compact window: the main window comes to the front with the capture screen (source `hotkey`) and after saving or closing returns to how it was: hidden, minimised, or behind the window that was in front. The app reports the closing of the screen (`captureRequestHandled`); the screen then sits on top of the inbox that is already running. A request that arrives while the app is still starting waits in the runner until the app listens.
  - **System tray** with the menu *New item* (source `tray`) / *Open* / *Exit*, also operable with the keyboard (`NOTIFYICON_VERSION_4`). The texts come from the ARB files through the app, in the active language. Closing the window hides it to the system tray, so that the keyboard shortcut keeps working; only *Exit* stops the app. That only applies if the system tray offers a way back *and* a way out: without an icon, or before the app has sent the menu texts (still starting, or a start error), the window simply closes (review T1.7 step B). No automatic start at sign-in.
  - If a capture screen is already open (through the button or an earlier request), a request does not open a second screen over the typed text; the request counts as handled as soon as that screen closes. If the user chooses *Open* themselves during capturing, the window stays open afterwards.
  - **Pitfall (found in the manual test):** Flutter reads the modifier keys with `GetKeyState`, the state its own thread saw last. The keyboard shortcut arrives with Win and Shift pressed, but the release goes to the window that was in front; Enter therefore arrived as Win+Enter and gave a new line instead of saving. The runner therefore waits until the keys are released (at most 1 s), sets the key state of its own thread to the real one (`SetKeyboardState`) and only then activates the window. Widget tests do not see this; the check is `tool/check_windows_shell.ps1`.
- **Implementation Android share menu (T2.1, 27-09-2026; PO decisions 27-09-2026).** Text and links (`text/plain`) come in through an exported `activity-alias` (`ShareCaptureActivity`) to the same native window as the widget; the window itself stays unexported. Another app can offer text this way, but never save it: the user taps Save themselves.
  - The window opens pre-filled (`SharedText.compose`): the subject (`EXTRA_SUBJECT`, for example the mail subject or page title) on the first line, the text (`EXTRA_TEXT`) below it; if the subject is already in the text, only the text. Everything exactly as received, line breaks included (DD-004). You can still add `@who` or a date; saving goes through the same queue, with source `share`.
  - The field shows line breaks, but the keyboard sees one line (`setRawInputType`) and shows the action key, which saves; typing yourself therefore adds no lines (PO decision 25-09-2026). This also applies to the widget.
  - If something is shared while the window is still open with unsaved text, the shared text goes below it: nothing typed is lost.
  - A hardware Enter saves, also with Shift or Ctrl: the field is multi-line to show shared lines and would otherwise add a line. The source stays `share` after rotating the screen. Unreadable extras from another app are ignored (review T2.1).
  - A URL stays plain text: no preview, nothing fetched (SPEC §4, REQ-003).
  - Files and photos follow with the attachments (T5.8); Offload is not in the share menu for those yet.
  - **Windows: no share menu (platform difference).** The Windows share contract only works for apps installed as a package (MSIX); Offload is not. On Windows text comes in by pasting into the capture screen (PO decision 27-09-2026).
- **Performance goal REQ-001:** the widget's input screen loads no lists or heavy state; saving happens first, parsing and indexing afterwards.
- **Photo of handwriting (REQ-064; PO decisions 09-10-2026, spike S6) 🔍.** A new channel on both platforms: photo → offline recognition (DD-002) → one candidate per thought on a review screen → after confirming, each kept candidate is captured as typed text (inline parsing DD-004, status `inbox`). Only offered when a verified model is imported; the photo is discarded after confirming and never becomes an attachment. Quick text capture (REQ-001) does not load the model. The design of the screen follows after S6.
- **Offload bar (REQ-063; PO decisions 06-10-2026, SPEC Q39–Q42).** A second widget, see DD-019. Its *Vastleggen* button opens `QuickCaptureActivity` exactly as the capture widget does (source `widget`; Flutter is not started). *Vandaag* and *Inzicht* start `MainActivity` with an extra naming the destination, through the path a reminder tap already uses (`ReminderChannel.takeOpened`, `onNewIntent`, put back when the app does not listen yet), generalised to "open a destination". The app does what a reminder tap does (`ReminderSync._open`): end an open triage or weekly review, pop back to the shell (the item detail saves on leaving), and set the destination; a capture screen with typed text is not popped (Q40; a reminder tap gets the same fix), and neither is what lies below it (an open item stays under the capture screen). *Implementation (T1.11, 06-10-2026):* `ReminderSync._open` knows `#today` and `#insights` (`lib/domain/app/open_targets.dart`) and stops popping at a `CaptureRoute` whose `hasText` is set by the capture screen; the widget's Today and Insights buttons start `MainActivity` with the reminder's open action and `NEW_TASK | SINGLE_TOP`, which brings the running app to the front (one `MainActivity`, checked on the emulator); the app shortcuts go through `OpenDestinationActivity` (no UI, a task of its own), because the launcher clears the task of a static shortcut. After *Force stop* Android cancels every PendingIntent of the app, the widgets' too, until the app is opened again (as for reminders, DD-005). A request counts once: `MainActivity.onCreate` drops the open action of an intent it gets back when it is recreated after the process died or started from Recents (`savedInstanceState`, `FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY`); before, the app then opened the old destination or item again, also after a reminder tap (found in the review, reproduced on the emulator). **App shortcuts (Q41a):** static shortcuts (`res/xml/shortcuts.xml`) with the same three actions and the same intents, labels from the ARB files; no permission. The Windows tray menu stays as it is (Q41b). DD-018 point 5 stays: the app starts on *Today* unless such a request names another place. The widget reads nothing and stores nothing (DD-007).

**Realises:** REQ-001, REQ-002, REQ-009, REQ-017, REQ-063, REQ-064.

## DD-013 · Manual sync through encrypted change packages 🔍

**Context.** The product owner uses Offload on a work phone *and* a work laptop and wants to keep them in step. Automatic sync (LAN, cloud) was rejected because the app would then need network access (DD-003, REQ-003). The app can make and receive a file though; we leave the transport to apps that already have the network (Signal, mail) or to a USB cable.

**Choice.**
- **Change package (`.offload`):** contains the entries from the change log (REQ-037) that the other device does not have yet, plus optionally the matching attachments. Per paired device it is tracked up to which HLC it has been updated. A full package stays possible (first time, recovery).
- **Encryption:** AES-256-GCM with the pairing key. A header with format version, sender device id and HLC range is authenticated along with it (AAD).
- **Pairing:** by default through a QR code with a random 256-bit key (strongest key, nothing to remember). Fallback: a passphrase, derived through Argon2id as for the backup (DD-007). The pairing key is stored encrypted with the device key. ⏳ Scanning may need `CAMERA` and a scanning library (SPEC Q13).
- **Merging:**
  - idempotent and order-independent: a log entry with an already known combination (entity, id, HLC) is skipped;
  - per field last-writer-wins on the HLC;
  - exception `rawText`: changed on both sides since the last common version → a conflict copy as a new item in the inbox, with an `ItemLink` to the original;
  - tombstones win over older changes;
  - tokens are derived again after import (DD-003);
  - people and tags with the same name → a merge proposal in the UI; the merge itself also becomes a log entry, so that the other device follows.
- **Import is one database transaction.** If something fails, nothing changes.
- **Transport:** out through `ShareChannel` (DD-014); in through the share target (Android, T2.1), file picker, drag and drop or a file association (Windows).

**Alternatives.** LAN sync (rejected, DD-003). A shared folder with Syncthing (parking lot; Syncthing itself has the network, Offload does not — can use the same package format later). CRDT per text field (more precise merging, but heavy and not needed for one user with two devices). An unencrypted package (rejected: mail is not an end-to-end channel).

**Consequences.** The format of the change log becomes an exchange format and must therefore be stable and versioned (REQ-037, before T1.6). Packages with attachments can exceed the mail limit (about 20–25 MB, varying per provider — *common knowledge*); attachments are therefore optional and a warning follows above a threshold.

**Realises:** REQ-035, REQ-036 (and makes REQ-037 necessary).

## DD-014 · Sharing through one ShareChannel 🔍

**Context.** Three features send something out: sharing an item (REQ-043), a vCard (REQ-040) and a sync package (REQ-035). Without a common abstraction there would be platform code three times.

**Choice.**

```dart
abstract class ShareChannel {
  List<ShareTarget> get textTargets;
  Future<ShareResult> shareText(String text, {required ShareTarget target, String subject, String fileTypeName});
  List<ShareTarget> get fileTargets;
  Future<ShareResult> shareFile({required String fileName, required String mimeType,
      required ShareTarget target, required Future<void> Function(File) write, String subject});
  // files: .offload backup (T7.2a); later .vcf, the sync package, attachments (REQ-044)
}
```

- **Android:** an own thin Kotlin implementation with `ACTION_SEND` (text) and a `FileProvider` URI (file). No plugin needed; if it does become a plugin, then through the dependency review of DD-008.
- **Windows:** the clipboard and "Save as…" always work. The Windows share window may not work without package identity *(uncertain; see also SPEC Q2 about MSIX)* and is therefore an extension, not a requirement.
- **Sharing an item as text (REQ-043):** an `ItemShareRenderer` in `domain/` turns an item into plain text: tokens converted (`@Jan` → "Jan", `!vr` → the date written out), `#tags` and `*priority` left out by default. The user sees and edits the result in a preview; only what is there goes out. The preview does not change the item.
- **Files the app creates for sharing** (vCard, package) are either a deliberate choice of the user to share (vCard) or encrypted (package). The temporary copies in the app's own cache or `FileProvider` folder are cleaned up on a next start; a file the user puts somewhere themselves through "Save as…" is never deleted by the app. When cleaning up is safe (a mail draft sometimes reads the attachment only later) falls under SPEC Q12; for the encrypted backup it is decided (T7.2a below), for the vCard and attachments it is still open.
- **Later (Could):** sending attachments along (REQ-044) needs temporarily decrypted copies; when they may be cleaned up is open (SPEC Q12). Showing an item as a QR code (REQ-045) reuses the QR display of the pairing (DD-013).

- **Implementation T2.7 (30-09-2026; PO decisions 30-09-2026).** Only text for now; `shareFile` follows with the vCard (T3.7), together with the `FileProvider` and the clean-up rule (Q12).
  - `ShareChannel` (`lib/platform/share/`) names its targets per platform instead of one call: `textTargets` is `system` on Android and `clipboard` plus `file` on Windows, and `shareText(text, target:, subject:, fileTypeName:)` sends to one of them. The screen shows one button per target and holds no platform code. `ShareResult` is `done` or `cancelled` (the save window closed); Android does not say whether the user really sent it, so there `done` means "handed to the share menu".
  - **Android:** `ShareChannel.kt` on the channel `eu.marandos.offload/share` starts a chooser with `ACTION_SEND` (`text/plain`, `EXTRA_TEXT`, `EXTRA_SUBJECT` when not empty); Offload's own share target is left out of the chooser (`EXTRA_EXCLUDE_COMPONENTS`). No permission.
  - **Windows:** the clipboard through Flutter's `Clipboard`; "Save as…" through `windows/runner/save_dialog.cpp` (`IFileSaveDialog`, owned by the app window, channel `eu.marandos.offload/save_dialog`). The runner only picks the path (overwrite prompt included); the app writes the file itself as UTF-8 with Windows line ends. The proposed name is the subject without the characters Windows forbids, at most 60 characters, never a reserved device name (`CON`, `LPT1`, …), otherwise "Offload". A modal window called from Dart through `dart:ffi` would stop the app drawing; from the platform thread it behaves like any window.
  - `ItemShareRenderer` (`lib/domain/items/item_share_text.dart`): `@jj` becomes "jj" **as typed** (PO decision; the full name of the linked person is a question for the PO after some use, see `BACKLOG.md` Parked); a date word becomes the date written out in the UI language (`itemShareDate`: "vrijdag 2 oktober", with the year only when it is not this year), taken from the stored tokens as in the detail, so an old `!morgen` keeps its date; `#tags` are left out, with the one run of spaces they leave; the switch "Include tags" keeps them as typed. `*priority` did not exist yet; it came with T10.5 and stays as typed, outside the switch (PO 09-10-2026: keep it so, AC REQ-043). An escaped `\@Jan` goes out as "@Jan". Pattern tokens and anything else stay as typed.
  - **Preview** (`lib/presentation/items/share_preview.dart`): the share icon in the top bar of the item detail opens a dialog with the switch, the editable text and one button per target. It starts from the text in the field, also before it is saved. What goes out is exactly the text in the field; the subject (share menu) and the proposed file name are its first non-empty line, so nothing leaves that was not in the preview. Toggling the switch makes a new proposal, which replaces edits made so far. An empty text cannot be shared. After copying or saving a message confirms it; a closed save window keeps the preview; a failure says so and keeps it too.

- **Implementation T7.2a (09-10-2026; PO decisions 09-10-2026): files, first the backup.**
  - `ShareChannel` gets `fileTargets` (Android `system`, Windows none: there a feature saves its file with "Save as…" itself, for the backup the `BackupFilePicker`) and `shareFile(fileName:, mimeType:, target:, write:, subject:)`. Like `BackupFilePicker.saveBackup`, the channel gives the place and the feature writes the file: the Android side empties the share folder (`prepareShareDirectory`), `write` writes the file there, and only then the file goes to the share menu. When `write` fails the half file is removed and nothing is shared.
  - **Android:** `ShareChannel.kt` starts a chooser with `ACTION_SEND`, the given type, `EXTRA_STREAM` plus `ClipData` and `FLAG_GRANT_READ_URI_PERMISSION` (the chooser passes the grant to the app the user picks), Offload's own share target left out as for text. The URI comes from `androidx.core.content.FileProvider` (authority `eu.marandos.offload.share`, `android:exported="false"`, `android:grantUriPermissions="true"`), whose paths (`res/xml/share_paths.xml`) hold only `cache/share/`; a file outside it is refused. `androidx.core:core:1.13.1` was already in the release through the Flutter embedding; `android/app/build.gradle.kts` names it with exactly that version (PO), so the APK holds no new library. No permission.
  - **Clean-up (SPEC Q12 for the backup):** the share folder holds one file: a new share replaces the previous one. A file left behind is removed at the next app start once it is older than 24 hours (`ShareChannel.removeOldShares`, from `MainActivity` on a background thread; never from the capture window, CLAUDE.md rule 7), so a mail draft can still read it later that day. The backup is encrypted, so the copy in the cache meanwhile reveals nothing.
  - **The export (T7.3, PO 09-10-2026)** shares through `shareFile` too, unencrypted, under the same rule (one file, replaced, removed after 24 hours): the share folder is the app's private storage on an encrypted device, and the export is the user's deliberate choice.
  - A vCard (T3.7) and attachments (REQ-044) reuse `shareFile`; how long *their* copy may stay is still SPEC Q12.

- **Implementation T2.7a (09-10-2026; PO decisions 09-10-2026): sharing as typed.** The preview gets a switch *As typed (for Offload)* (NL "Zoals getypt (voor Offload)", with the line "With @, #, ^, * and fixed dates: Offload on another device makes an item with the same text and tokens of it."). On, the field holds `ItemShareRenderer.renderAsTyped`: the raw text with every token as typed, only a date word replaced by `!d-m-yyyy` from the stored date (`knownDates`, as in `render`), so the deadline stays the same day whenever the text is read; repeat words stay, escapes stay. *Include tags* is hidden then (tags always go along). The receiving side is the existing share target (T2.1) or pasting into *Capture* on Windows: the token processor reads the text again, so `@Jan` resolves to a person of that name (or makes one, DD-015), `^project` and `[[…]]` resolve by name or get the existing "no project"/"no item" chip. Only text travels: not the status, type, a project chosen in the picker, the note or the "Where was I" note; a lossless item file stays rejected for v1 (below; M9 covers it). Offload's own share target stays left out of the chooser (PO): sharing to oneself on the same device would only duplicate the item.

**Alternatives.** Sharing an item as an `.offload` file for another Offload user (rejected for v1: in practice the only other Offload user is the owner themselves, and DD-013 covers that). A ready-made share plugin (possible, but own code is small and keeps the dependency list short).

**Realises:** REQ-014 (sharing a backup), REQ-040 (transport), REQ-043, REQ-044, REQ-045.

## DD-015 · People as a light entity ✅ 🔍

> ✅ approved by the product owner (27-09-2026) · 🔍 review by the architecture agent.

**Context.** The commitment ledger (REQ-046, REQ-047), the people view with commitment balance (REQ-048) and smart quick capture (REQ-050) all hinge on the question "who?". The entity Person already exists (SPEC §7, schema v1: `people` and `person_aliases`), with the profile from DD-012 on top. Still open was how people come into being and how they are maintained.

**Choice.**
- **A person is a light entity:** name and aliases. The profile (DD-012: birthday, note, contact details, organisation and job title) stays optional on top.
- **No separate field *role*** (SPEC Q23, PO decision 27-09-2026). *Job title* (REQ-038) is the job title; the relation to me (client, manager) fits in the free-form note. According to DD-012 a structured field only comes when it needs behaviour, for example grouping the balance by role. To be reconsidered once the app has been in use for a while.
- **`@Name` in quick capture creates the person if they do not exist yet.** That happens in the parse step *after* saving, never as a condition for saving (REQ-001, hard rule 7). The suggestion list already offers "New: create …" (REQ-033); this decision makes creating also the result of saving with an unknown name.
- **Recognition** is by name and aliases, case-insensitive. For Cyrillic that must be Unicode-aware (see the point of attention in DD-003).
- **Grammar of `@`:** only a token at the start of the text or after white space, as with `*` (DD-004 point 3). The pattern token email address goes first: `jan@example.org` is an email address and never creates a person "example.org".
- **No duplicate people through concurrent creation:** the parse step after saving checks and creates in one transaction, or through one serial queue. Two quick captures with the same unknown `@Jan` yield one person.
- **Renaming:** the old name becomes an alias. `rawText` is never rewritten (DD-004 point 1), so `@Oldname` in existing items must still point to the same person when parsed again.
- **Merging** (A into B): all references to A (requester, waiting for, commitments, contact details, attachments) go to B; the name and aliases of A become aliases of B; A gets a tombstone and a reference `merged_into_id` to B. Everything runs through `ChangeLogWriter` in one transaction, so that the merge is replayable and travels along in sync (ties in with the merge proposal in DD-013). Derived tokens are rebuilt afterwards.
  - **Late references:** an item that started to refer to A on another device at the same time ends up with a deleted A after sync. When reading and on import `merged_into_id` is therefore followed, so that such an item still belongs to B (review architecture agent 27-09-2026).
  - **Duplicate aliases** (an alias of A already exists on B) are stored once.
  - Merging changes `requester_id`/`waiting_on_id` of the items involved and so gives them a new HLC; for stale detection (REQ-051) they count as touched afterwards. Deliberately accepted.
  - ~~*Proposal, for review:* with conflicting profile fields the user chooses~~ — superseded by the PO decision of 01-10-2026 (DD-018 point 7, Merging): B keeps what it has, an empty field takes the value of A; free-form notes are put one after the other, not thrown away.
- **No contact import.** No `READ_CONTACTS`, no import from the contact list (confirms DD-012 and the empty permission list of DD-008).

**Alternatives.** *People as tags* — rejected: tags cannot be renamed or merged without rewriting the raw text. One typo then yields a second "person" without a way to repair it, which makes the people view and the ledger unreliable. *Contact import* — rejected: needs a permission and turns the app into a CRM (DD-012).

**Consequences.** Creating automatically means that typos yield extra people; merging is therefore necessary, not an extra, and must be there before or together with smart quick capture (T10.5). Renaming and merging are writes to several tables in one transaction.

**Realises:** REQ-012, REQ-046, REQ-047, REQ-048, REQ-050.

## DD-016 · Search in two steps: FTS5 foundation and advanced search ✅ 🔍

> ✅ split approved by the product owner (27-09-2026) · 🔍 implementation for review by the architecture agent.

**Context.** DD-001 chose SQLite FTS5 for REQ-011. In T1.4 it was established that FTS5 is in the sqlite3mc build, but only with a unit test on the development machine (`test/data/database/database_encryption_test.dart`), not on Android. Links between items (REQ-054, autocomplete) and duplicate detection (REQ-053) depend on the index.

**Choice.**
- **Two steps.** The *foundation* (T2.5, priority high) comes early, because links and duplicate detection build on it and a platform problem must become visible early. *Advanced search* (T10.13, priority medium) builds on it.
- **Foundation:**
  - An FTS5 table through Drift over the titles, text and notes of items, person notes and contact details (AC REQ-011, REQ-031, REQ-038) and transcribed speech (T6.3).
  - Tokenizer `unicode61 remove_diacritics 2` (diacritic-insensitive: "categorie" finds "catégorie"), prefix search with a prefix index, ranking with `bm25()` (title weighs more than text).
  - **Indexing happens *after* saving** (hard rule 7, REQ-001, DD-010; tightened after review 27-09-2026). SQLite triggers on the source tables only put the table and id of the changed row in a small local queue `search_pending` within the save transaction; the actual FTS work does not happen there. An indexing task processes the queue directly after saving, and on every start as a safety net. That way a capture never waits for the index, and the triggers also catch rows written by `ChangeLogReplayer` or a sync import. A row with a tombstone leaves the index.
  - The FTS index is derived, local data, like `tokens`: no HLC, tombstone or change log, never in a sync package, and rebuildable at any moment (after sync, restore or another tokenizer). That does not clash with DD-003: "log in Dart, not with triggers" is about the change log, and these triggers write no log. The exception is also in the list of DD-003.
  - **No external content on `rowid`.** All synchronisable tables have a text UUID as primary key; their `rowid` is implicit and can change on `VACUUM`. An external-content table on `rowid` then silently points to wrong rows. Therefore *either* a plain FTS5 table with its own content and the columns `entity` and `entity_id` (`UNINDEXED`), plus a small derived mapping table (`INTEGER PRIMARY KEY` ↔ entity and UUID) so that deleting is not a full scan; *or* `contentless_delete=1` (SQLite ≥ 3.43, check against the bundled sqlite3mc version). Choice in T2.5.
  - **Rebuilding** happens from the source tables (empty the index and fill it again); the FTS5 command `'rebuild'` only exists for external-content tables.
  - The index is in the encrypted database; no extra measure is needed.
  - **Verification on both platforms** with an integration test (Android and Windows): FTS5, `remove_diacritics 2` (needs SQLite ≥ 3.27), prefix query and `bm25()`. For T10.13 right away also whether the `trigram` tokenizer is available (SQLite ≥ 3.34). *(version requirements: common knowledge, check against the bundled sqlite3mc version)*
  - **Duplicate detection** runs *after* saving, asynchronously, and never blocks (REQ-001). A strong match becomes a hint "Does this already exist?" in the inbox and in triage.
  - A basic search screen from the top bar (DD-011).
- **Advanced search (T10.13):** phrase and `NEAR` queries, `snippet()`/`highlight()` in results, saved searches as smart lists, and an evaluation of the `trigram` tokenizer for searching on part of a word (trade-off: index size; diacritic insensitivity for trigram needs a newer SQLite, *uncertain*).
- **Cyrillic:** `unicode61` folds case outside the Latin alphabet too *(common knowledge; check in T8.6)*.

- **Implementation step A (T2.5, 27-09-2026; PO decisions 27-09-2026).** Schema v2, the first migration (step by step through `drift_dev make-migrations`, schema dumps in `drift_schemas/`, migration test in `test/drift/`). Everything in `lib/data/database/search.drift`:
  - `search_index`: a plain FTS5 table with its own content (columns `title` and `body`, `unicode61 remove_diacritics 2`, `prefix = '2 3'`), so that T10.13 can show fragments; no `contentless_delete`. `search_map` maps the own `INTEGER` key (the rowid of the index) to entity and UUID; `search_pending` is the queue.
  - Triggers on `items` (only when `raw_text`, `title`, `body` or `deleted_at` changes), `people` (`name`, `note`, `deleted_at`; since schema v7 also `organisation` and `job_title`), `person_aliases` and, since v7, `contact_details` put the entity in the queue (a contact detail queues its person). A change of, for example, `due_at` therefore costs nothing.
  - Searched: items with the title as `title` and the raw text plus note as `body`; people with name and aliases as `title` and the note as `body` (people also by name and alias: PO decision). `bm25` with weight 10 for `title` and 1 for `body`. Transcriptions (T6.3) are added once that table exists: an entity name and trigger of their own, nothing more. *Contact details (T3.5, 02-10-2026) went differently:* they are part of the person's `body` (with the organisation and job title), because a hit on a phone number should show the person, not a detail of its own.
  - The query is converted in the domain (`ftsMatchExpression`): every word a quoted prefix term (`"keur"*`), all words must occur; FTS5 syntax in the input is plain text and never gives an error. When searching it is also checked that the item or person is not in the trash, so that a just-deleted item never appears, not even before the indexing task has caught up.
  - `DriftSearchIndex.keepUpToDate` indexes at start-up and after every change Drift reports in `items`, `people`, `person_aliases` or (since v7) `contact_details`; runs never overlap. Every entry gets its own short transaction and only then leaves the queue; a save therefore waits for at most one such transaction. An entry that fails stays for the next run. The migration puts all live items and people in the queue; the index then fills after the start. Rebuilding (`rebuild`) is internal; there will be no button for it (PO decision). The queue is read in blocks of 200, in key order; an error only goes into the local development log.
  - **The migration is atomic:** Drift does not run migrations in a transaction. All steps and the new version number (`PRAGMA user_version`) therefore go together in one transaction: a stop halfway leaves nothing behind, and the next start tries again (review T2.5). This pattern applies to every following migration.
  - There are no `AFTER DELETE` triggers: nothing is deleted physically now (trash = tombstone). A later task that deletes physically (emptying the trash, cleaning up) must take the index along; until then the check when searching keeps such rows out of sight.
- **Implementation step B (T2.5, 27-09-2026; PO decision 27-09-2026):** a plain search screen (`lib/presentation/search/search_screen.dart`), opened with a magnifying glass in the inbox's top bar; the styling follows in Q5b. It searches on every keystroke (the local index is fast); an answer for older text is ignored. Items and people are in one list, best hit first, with an icon (with a screen-reader label) per kind: an item shows its title or else the raw text and the moment of capture, a person the name and the first line of the note. The search query supplies that data itself (`SearchHit.title`, `text`), with the same check on live rows. Tapping does nothing yet: the item detail comes with T2.3. Without input the screen explains that the start of a word is enough.
- **Implementation step C (T2.5, 27-09-2026; PO decisions 27-09-2026): "Does this already exist?" (REQ-053).**
  - The rule is in the domain (`lib/domain/search/duplicates.dart`, `looksLikeDuplicate`): after folding away case, diacritics and the signs `@#!` it is *either* the same text, *or* at least 80% of the meaningful words (3+ letters) of the shorter item are in the other, and there are at least 3 of them. Rather no hint than a wrong one (different word forms do not count as equal).
  - Candidates come from the index (`itemsSharingWords`: live items with at least one whole word in common, `bm25` order, at most 20); the rule decides. Finished items count, items in the trash do not; only items, no people (merging people: DD-015).
  - The hint only belongs to the newer item of a pair (UUIDv7 sorts by time). It is computed every time, never stored (hard rule 6), and looked at again when the index changes (the indexing task reports `search_map` to Drift after every run with work) or when a pair is ignored.
  - In the inbox "Looks like another item" (NL: "Lijkt op een ander item") is shown below the item; tapping opens a dialog with both texts and **Ignore** or **Close**. Open and link from the AC come with the item detail (T2.3) and links (T10.9). Nothing is ever merged or deleted. *T10.9 (03-10-2026, DD-004 point 13):* linked pairs are no candidates, and the text inside `[[…]]` is left out of the comparison, so an item that links to another does not look like items similar to its target.
  - **Ignore** is user data and is synchronised: table `duplicate_dismissals` (schema v3, `SyncColumns`, through `ChangeLogWriter`), one row per pair with the smallest id first (`CHECK (item_id < other_item_id)`), so that the choice applies to both directions. The migration follows the atomic pattern of step A.
  - **Measured (integration test, 27-09-2026):** on Android (emulator) and Windows SQLite 3.53.4; FTS5, diacritics, prefix and `bm25` work; the `trigram` tokenizer is there, also with `remove_diacritics`. Capturing with and without the triggers is equal within the measurement noise (Windows 8.6 ms against 8.7 ms; emulator two runs: 41.9 against 37.8 and 39.8 against 42.8 ms).

**Alternatives.** *Everything in one step* — rejected: links and duplicate detection would then wait for low-priority features, and a platform problem stays invisible for a long time. *`LIKE` search* — slow on large text, no ranking, not diacritic-insensitive. *A separate search library* — extra dependency and native code (DD-008), and an index outside the encrypted database.

**Consequences.** The database grows (index, prefix index, later possibly trigram). A rebuild path is needed ("rebuild index"). Directly after saving an item may briefly not be findable yet; duplicate detection therefore waits for the indexing task. Adding the index is a schema migration.

**Realises:** REQ-011, REQ-053, REQ-054, REQ-058.

## DD-018 · Layout per screen (design round Q5b) ⏳

> ⏳ in progress: per screen a decision of the product owner, with a sketch in [`docs/design/screens/`](docs/design/screens/README.md). Where they differ, this text wins over the sketches.

**Context.** SPEC Q5b asks for the layout per screen before the UI is built. - **Windows:** thumbnails take focus with <kbd>Tab</kbd>; <kbd>Enter</kbd> opens, <kbd>Del</kbd> asks to delete; <kbd>Esc</kbd> closes the viewer.
- **(f)** A business card on a person (T3.8) comes later with the same parts.

**Undo messages (28-09-2026):** a message with Undo (trash, triage, and completing from Today) goes away after 5 seconds. Flutter would keep a message with an action on screen until tapped; that stays only when a screen reader is on (REQ-016), because reaching the button then takes longer (`undoSnackBar`, `keepUndoMessage`). **A new message replaces the previous one (29-09-2026):** Flutter queues messages, so behind a message that stays, every later one (the undo of the next swipe, a failure) would wait unseen. Every message in the app therefore goes through `showMessage` (`lib/presentation/messages.dart`), which clears the current and queued messages first; the undo of an earlier choice then ends with its message, as in triage. Only TalkBack keeps a message: the Flutter Windows embedder never reports accessible navigation, so with Narrator it still leaves after 5 seconds (follow-up in T8.2).

## DD-019 · Widget icon: "drop one in" ✅ 🔍

> ✅ design by the product owner (28-09-2026) · 🔍 review by the architecture agent. Details, rejected alternatives and the file list: [`branding/widget/WIDGET_ICON.md`](branding/widget/WIDGET_ICON.md). Artwork in `branding/widget/` and `branding/`; not redrawn in the code.

**Context.** The capture widget (REQ-001) was a text-only button of 2×1 cells, too big for what is one button (PO feedback 28-09-2026). The app itself still had the default Flutter icon, while the Offload artwork was ready in `branding/`.

**Choice.**
- **The widget icon reuses the form language of the app icon and changes exactly one thing.** The app icon is the tray with three amber dots falling in ("what is in it": the stored thoughts); the widget icon is the same tray with **one** larger amber dot with a knocked-out **+** ("drop one in now": capturing). Same colours: navy `#22304F→#151E33`, tray `#F1F5FB`, amber `#E9A23B`. Side by side on the home screen they are related but not interchangeable.
- **Glyph:** `widget_glyph.svg` (24 dp, monochrome) becomes the VectorDrawable `res/drawable/ic_widget_capture.xml`, converted by hand: the tray as a round stroke, the dot as a fill with `android:fillType="evenOdd"` for the knocked-out plus; no masks. The widget tints it with a colour resource (`@color/widget_glyph`), never a hardcoded colour.
- **Size: 1×1 by default**, resizable horizontally. From about 180 dp wide the widget shows a wide variant: the glyph plus the hint "Capture something…" (NL: "Leg iets vast…"). `CaptureWidgetProvider` hands the launcher both layouts (`RemoteViews` with a size map, Android 12+); the launcher picks the largest that fits. The whole tile or bar is the button, as before.
- **Background:** the navy tile of the app icon, with the system widget corner radius (`system_app_widget_background_radius`).
- **Preview:** `android:previewLayout` (the real 1×1 layout, so it follows language and theme; minSdk 33); `previewImage` (`widget_icon_192.png`) only as a fallback for launchers without it.
- **Texts through ARB** (DD-009): the name in the widget picker and the accessibility label "Capture" (NL: "Vastleggen", existing key `captureAction`), the hint `androidWidgetHint`; generated into Android resources by `tool/gen_android_strings.dart`.
- **Not built:** the microphone button of the 4×1 mock in `widget_preview_sheet.png`. It is a proposal, not a decision; it belongs to REQ-006 and needs its own trade-off (starting a recording from the widget).
- **Dynamic colour (Material You)** is not applied yet: the widget keeps the fixed navy tile. The design note suggests tinting the glyph with the system colour and keeping the amber dot (duotone) — for T8.1.
- **App icon (28-09-2026, same PO request).** Android: an adaptive icon (`mipmap-anydpi/ic_launcher.xml`) with the background, foreground and monochrome layers from `branding/icon_*.svg` as VectorDrawables; the monochrome layer gives a themed icon. minSdk 33, so no bitmap fallbacks: the default Flutter PNGs are gone. Windows: `windows/runner/resources/app_icon.ico` (16–256 px, PNG-compressed) generated from `branding/icon_app_512.png` by `tool/gen_windows_icon.ps1` (System.Drawing, no extra tool). The system tray uses this app icon until it gets its own icon (T8.9).
- ⏳ **16 px for the Windows system tray:** downscaled, the `+` of the widget glyph closes up into a dot. Readable as "dot in a tray", but a sharp result needs a hand-pixelled 16 px variant for the `.ico` (SPEC Q25).

- **Offload bar (REQ-063; PO decisions 06-10-2026, SPEC Q39–Q42; sketch `21-offload-bar`).** A **second provider** (`OffloadBarWidgetProvider`) with its own entry in the widget picker, "Offload-balk" (EN "Offload bar"), so the 1×1 capture widget and its wide variant keep their function (their height changed with this task, see *Height* below). Default 2×1, resizable horizontally to 3×1; a size map hands the launcher a two-button and a three-button layout (the second from about 180 dp wide, as the wide capture variant). The same navy tile with the system corner radius, light and dark alike (Material You stays for T8.1). Each button is an icon with a short label below it (the navigation bar's words: *Vastleggen*, *Vandaag*, *Inzicht*), at least 48 × 48 dp, with its own `contentDescription` from the ARB files. Icons: the capture glyph `ic_widget_capture` (this DD) and the navigation bar's *Today* (`wb_sunny`) and *Insights* (`insights`) icons as VectorDrawables (Material Icons by Google, the same icons the app already ships in Flutter's icon font, under the licence Flutter ships with that font, CC BY 4.0; it is listed in *About Offload* as "Material Icons (Google)", REQ-062; the shortcut icons are recoloured on a navy circle, which that licence allows when said, as here). `previewLayout` is the real 2×1 layout. No counts, no content, no database (DD-007).
  - *Implementation (T1.11, 06-10-2026):* `OffloadBarWidgetProvider` (`capture/`), layouts `widget_bar` and `widget_bar_wide` (from 180 dp), `ic_bar_today` and `ic_bar_insights` (Material Icons as VectorDrawables), `xml/offload_bar_info.xml` (2×1, resizable), `xml/shortcuts.xml` with three static shortcuts and their icons. RemoteViews allow no plain `View`, so the line between buttons is a `FrameLayout`. Strings `bar_*` and `open_*` from the ARB files (`tool/gen_android_strings.dart`). The licence of the Material icons (the text Flutter ships with its icon font, which the app already carried without it being listed) is in `bundledLicenses`.
  - *Height (PO 06-10-2026, while building):* a widget no longer fills its launcher cell, which on the test device is about 140 dp high: the bar is a strip of `@dimen/widget_height` (60 dp) in the middle; the 1×1 capture widget became a square tile of 60 × 60 dp and its wide variant a bar of 60 dp. `@android:id/background` is on the tile, inside a transparent frame, so the system corner radius and launch animation apply to the tile.

**Alternatives.** A pencil or notepad (generic, no relation to Offload). An arrow down into the tray (reads as "download": the wrong association, certainly for an offline app). A microphone as the main motif (puts the emphasis on speech, REQ-006 Should, while text, REQ-001 Must, is the primary channel). Two separate widgets in the picker (1×1 and wide) instead of one resizable widget: more choice in the picker, but two providers for one button.

**Consequences.** The widget is smaller and recognisable; an existing 2×1 widget keeps its size and shows the tile variant after the update. The wide variant depends on the launcher reporting the widget size (Android 12+, fine with minSdk 33). The layout of the widget now has two variants to keep in step.

**Realises:** REQ-001, REQ-017 (tray icon, prepared), REQ-063 (Offload bar); texts per REQ-005 and REQ-029.

## DD-020 · Help in the app: the manual, rendered from Markdown 🔍

**Context.** The user manual (`docs/user-manual/`) is kept up to date with every release build, but lives only in the repository. The PO wants it inside the app, reachable from Settings and from each screen (REQ-065, PO decisions 09-10-2026).

**Choice.**
- **Renderer:** the `markdown` package (Dart team, tools.dart.dev, pure Dart; brings `args`, and `meta` that is already shipped) parses; an own widget renderer in `presentation/` builds Flutter widgets for the subset the manual uses (headings with ids, paragraphs, lists, bold/italic, inline code, code blocks, links, tables), in IBM Plex, following the theme and text size. The same renderer serves Markdown in notes (T10.10). Both packages are added to `tool/allowed_packages.txt` with date and reason (DD-008, approved by the PO); their licences (BSD-3-Clause) appear under *About Offload* through Flutter's own overview, which collects every Dart package, so they get no entry in `bundledLicenses` (that list is for what Flutter does not collect; PO 09-10-2026, revising the first decision) (REQ-062).
- **Content:** the manual is bundled as assets from `docs/user-manual/en/` (English is the base, PO 09-10-2026; `nl/` follows with T8.5). The viewer opens the chapter in the app language and falls back to English with a note. Links between chapters and to headings are resolved inside the viewer, with its own back stack; an external link shows its URL only; nothing is loaded from outside the bundle.
- **Help in context:** one table (screen → `chapter.md#anchor`) drives a "?" per screen; a test reads the bundled chapters and fails on a missing chapter or anchor, so a renamed heading cannot silently break help.
- **The manual belongs to the build (process).** The documentation agent runs *before* a release build for use, not after it, so the bundled manual matches the built code. `tool/build_release.dart` computes the same content hash as `Get-DocsState` in `.claude/hooks/common.ps1`, which `mark-docs.ps1` records (the code state without `docs/user-manual/`, `docs/features.md` and `CHANGELOG.md`) and, with `--copy`, refuses to build when `.claude/.docs-marker` does not hold it; a test build without `--copy` only warns (PO 09-10-2026: not on every test round). The hook `docs-trigger`, which asked for the documentation agent *after* every release build, is removed: it would ask after every test build too; `mark-docs.ps1` stays and records the documented state, and a test compares its exclusions with the script's (T8.11).
- **Status out of the manual:** what the manual's index listed as "Status" and "Already built" moves to `docs/features.md`, kept by the documentation agent; the index becomes a task-oriented table of contents.

**Alternatives.** `flutter_markdown` (discontinued by the Flutter team in 2025; more dependencies). A WebView with HTML (a browser engine in an offline app, harder to prove network-free, DD-008). Plain text without formatting (tables and code blocks unreadable).

**Consequences.** One more pure-Dart dependency (two packages); the manual's assets grow the app a little (about 150 kB of text). The documentation agent writes English from now on; CLAUDE.md (language, agents and gates, Definition of done) changes with it.

**Realises:** REQ-065; supports REQ-055 (T10.10).
